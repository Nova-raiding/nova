## 实施前的架构评审（历史基线）

1. 已核实（10/10）：`server.ts` 的上传分支只调用 `validateCustomerDeliveryUpload(params)`，目前输入必须有 base64；`mcp.ts` 同样要求 name/mime/content。增加 URL 不能只改前端。
2. 已核实（10/10）：现有出站 `assertOutboundUrl` 先查 DNS，下载侧普通 fetch；任意合同链接必须把检查过的地址固定到实际 TLS 连接，不能复用为任意 URL 下载器。
3. 已核实（10/10）：交付仓储字段没有目标账号，密码账号身份和 account row key 不是同一概念；新增准入不能直接调用 activateMerchantAccount 覆盖管理员停用。

合同工程决定：既有 upload 方法增加 source_url，与本地文件输入严格互斥，仅 contract 用途开放；URL 分支不接收客户端 name/mime/hash。仅公开 HTTPS 直链，无凭据、无重定向、不请求私网；返回正文按字节识别并复用现有文件准入。失败不写成合同引用，不标记完成。

账号工程决定：独立准入与角色、身份、成员、工作区、付款、商业权益取交集，旧未绑定账号不自动受影响。正式业务入口及 worker 派发前需要实时检查；接入/恢复操作必须精确枚举，不可凭方法前缀豁免。此闭环独立交付，在正式接线和运行面验证前，UI 仍只声称“交付完成”。

## 代码质量评审

- 下载器独立小模块，无新增通用服务或第三方依赖；Node HTTPS 内置传输固定解析结果，保留证书验证。
- 文件和链接共享扫描轮询、取消、重试、素材匹配以及 ready/clean 校验，禁止复制出第二套“成功”判断。
- 错误只显示可恢复说明与错误码；不将签名 URL 的查询参数写入日志或业务审计。取消后不得自动登记。
- 共享 server.ts、mcp.ts 由 owner 负责；agent 仅修改明确分配文件。

## 性能评审

- 合同下载限制 50 MiB、总期限、流式累计并超限终止，不自动解压、不无限跳转。控制进程内并发，拒绝过载，不以 50 MiB 单文件限制冒充总资源限制。
- 账号读取应按 workspace + identity 索引查询，不扫描全部档案；不缓存可撤销的允许结论。worker 重新检查是授权要求，不可以吞掉异常后继续。
- 重型 PG/扫描/桌面验收串行运行，避免已观察到的扫描器内存不足；不停止或清空别人的容器。

### T5 实施约束与验收边界

- 密码账号行 `PasswordAccount.id` 与 `identityId` 在 PostgreSQL 中不同；OAuth 与密码会话应落到同一个稳定 identity。交付建档操作人不能作为目标客户。
- 已增加 `targetAccountId`／`targetIdentityId` 成对绑定；由同租户商家账号目录明确选择，界面显示登录账号。创建绑定时服务端再验证账号类型、实际成员关系及状态，不自动绑定第一个账号、不按公司名猜测、不把旧档案批量回填。
- 普通档案 patch 不能修改绑定；工作区内同 identity 不得绑定多份相互竞争的生效档案。迁移顺序需基于实际最新 registry 确认，现有 OAuth 210／211 迁移及其 RLS 不回改。
- 使用现有仓储 `get` → `readWithEvidence` 重新计算完成状态，不只读 `effective_at` 原始列。未绑定历史账号保持原行为；已绑定但档案不完整、证据失效或读取失败不能获得正式业务准入。
- 准入必须与现有身份、会话、成员、角色、管理员停用、付款和商业权益取交集；禁止调用账号启用方法来覆盖停用，不授予积分或订阅。
- MCP 与 HTTP 需在真实鉴权及能力检查后、业务副作用前统一接入；worker 在授权快照检查和最终 provider 派发前复核。登录恢复、明确接入步骤及运营验收需按精确操作列举，不能整组豁免“只读”或 onboarding 方法。
- 最低运行矩阵：同企业两个账号只影响绑定者；密码／OAuth 一致；跨企业拒绝；管理员停用仍阻断；凭证撤销后阻断；排队后及等待锁期间撤销不得调用 provider；拒绝路径无扣费或发点。单次读取后的异步派发不能冒充绝对原子撤销，需单独验证最终授权时序。
