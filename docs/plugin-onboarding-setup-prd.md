# 大麦 ChatGPT 插件：安装后系统引导配置 PRD

## 1. 背景与问题

当前插件安装完成后直接进入可用工具/业务对话，用户不知道：

- 第一步应该做什么；
- 需要绑定哪些身份、工作区和店铺；
- 哪些配置由平台管理员完成，哪些需要商家本人确认；
- 绑定成功后下一步是什么；
- 为什么某些能力仍然不可用，以及如何恢复。

结果是用户把“插件已安装”误认为“商家已接入”，遇到空数据、无权限、模型未配置或支付未就绪时无法自助排查。

## 2. 产品目标

为首次安装插件的商家提供一个可恢复、可解释、可验证的系统引导流程，让用户在 ChatGPT 对话中完成从“插件已安装”到“可以安全读取自己的商品并开始第一项任务”的最短路径。

### 成功标准

1. 新用户首次调用插件时，能看到当前配置状态、下一步和阻断原因。
2. 用户可以明确知道需要绑定：ChatGPT 身份、工作区、平台店铺、平台授权和可选的模型/支付配置。
3. 每一步完成后自动刷新状态，并只展示服务端授权的下一步。
4. 未完成配置时不执行商品同步、内容生成、发布或支付写入。
5. 所有状态都能通过 `request_id`、`trace_id`、`workspace_id` 和服务端证据追溯。

## 3. 非目标

- 不在插件内保存平台账号密码、access token 或支付密钥。
- 不把本地 fixture、示例商品或演示订单伪装成真实数据。
- 不在引导流程中自动发布、自动充值、自动生成正式内容。
- 不替代平台 OAuth 官方授权页、支付 provider 或运营审批系统。
- 不把 Merchant Studio 开发调试页面作为商家配置前置条件。

## 4. 核心用户旅程

```text
安装插件
  → 检查连接配置
  → 建立/恢复工作区
  → 检查商家身份与权限
  → 选择平台
  → 绑定店铺并完成官方授权
  → 检查数据可读性与创意点准入
  → 首次读取商品
  → 创建首个只读任务
  → 用户明确确认后才进入生成/发布
```

## 5. 引导入口与状态

### 5.1 入口

首次调用 `merchant.start` 时，插件必须先返回“系统引导卡片”；后续会话可通过以下任一说法重新打开：

- “配置大麦插件”
- “检查插件连接状态”
- “我还没有绑定店铺，下一步是什么？”

引导卡片应提供“继续配置”“查看全部步骤”“稍后再说”三个动作。选择“稍后再说”只关闭展示，不改变服务端状态。

### 5.2 配置状态模型

每一步使用 `not_started`、`in_progress`、`blocked`、`ready`、`needs_refresh` 五种状态。状态必须来自服务端事实，不由模型推断。

| 步骤 | 检查内容 | 完成条件 | 阻断示例 |
|---|---|---|---|
| 插件连接 | `MERCHANT_MCP_BASE_URL`、HTTPS、MCP 握手 | `initialize` 和 `tools/list` 成功 | 地址缺失、非 HTTPS、工具为空 |
| 用户身份 | Bearer/OIDC 身份映射 | 服务端返回有效 actor 与角色 | 未登录、token 过期、角色缺失 |
| 工作区 | `workspace.bootstrap` 或恢复 binding | 返回当前 workspace 且租户范围一致 | workspace 缺失、binding 失效 |
| 创意点准入 | `billing.status` / commercial access | `balance_state=ready` 且 access revision 有效 | unknown、余额不足、准入过期 |
| 平台选择 | 六个平台列表 | 用户明确选择平台 | 用户未选择或选择不支持平台 |
| 店铺绑定 | `platform.store.list` | 用户明确选择 `platform + account_id` | 同名店铺、多候选、撤权 |
| 官方授权 | `platform.connect` 与 OAuth callback | 服务端报告授权成功和可读 scope | callback 失败、授权过期、scope 不足 |
| 数据读取 | `workspace.health`、`catalog.search` | 至少返回真实店铺目录/商品事实 | API 未配置、同步失败、数据为空 |
| 首个任务 | 只读任务预览 | 用户看到商品、SKU、平台和事实来源 | 商品身份不完整、规则缺失 |

## 6. 每一步需要告诉用户什么

引导卡片每次只突出一个当前步骤，同时显示总进度，例如“第 3/8 步”。每一步必须包含：

1. 这一步是做什么的；
2. 用户需要提供/确认什么；
3. 系统会调用什么；
4. 成功后会得到什么；
5. 失败时怎么处理；
6. 当前是否会产生外部写入。

示例：

> 当前第 4/8 步：绑定淘宝店铺。请从已授权店铺中明确选择一家；我们只保存店铺标识和授权摘要，不保存密码。完成后可以读取该店铺的商品目录；本步骤不会同步、生成或发布内容。

## 7. 绑定设计

### 7.1 必须绑定

- ChatGPT/Codex 宿主身份：由宿主和服务端 Bearer/OIDC 提供；用户不可在插件中伪造角色。
- 工作区：首次由服务端创建或恢复；binding 按 API、身份和 token 指纹隔离保存。
- 店铺：必须使用 `platform + account_id`，不能只使用店铺名称，不能默认列表第一家。
- 官方平台授权：通过服务端 OAuth 官方流程完成，插件只展示脱敏结果。

### 7.2 可选配置

- 业务模型中转：由管理员配置，商家不填写 API key；缺失时生成能力明确显示“未配置”。
- 支付 provider：由平台服务端配置；未就绪时只能查看目录/订单状态，不能创建真实支付。
- 规则审批 token：仅运营审批流程注入，不写入插件清单或对话。

## 8. 完成后的下一步

当工作区、店铺、授权和数据读取均为 `ready` 时，插件显示三条明确路径：

1. “查看我的商品目录”（只读）；
2. “上传商品图片并建立素材档案”（需要素材扫描和事实确认）；
3. “创建首个营销任务”（先确认平台、店铺、SKU 和任务目标）。

生成、审核、批准、发布必须继续遵守现有独立确认链，不得因为“引导完成”而自动放开写权限。

## 9. 错误与恢复

错误卡片必须区分：

- 配置错误：缺少 MCP 地址、workspace 或 token；
- 权限错误：身份有效但角色/租户无权限；
- 外部授权错误：OAuth callback、scope 或 refresh 失败；
- 数据错误：API 超时、同步失败、空数据；
- 商业准入错误：余额 unknown、不足、revision 过期；
- 服务端错误：带 request/trace 信息，可重试但不得声称成功。

每类错误提供一个主动作：重新加载配置、重新授权、重试读取、切换店铺或联系管理员。重试必须幂等，不重复创建订单、任务或授权。

## 10. 安全与权限要求

- 引导阶段默认只读，除 `workspace.bootstrap` 等服务端明确允许的初始化动作外，不执行业务写入。
- 所有店铺级请求固定注入 `X-Workspace-Id`，并由服务端再次校验租户边界。
- `tools/list` 缺失、混入 `ops.*` 或 registry 未分类时失败关闭。
- 不显示 token、secret、credentialRef、原始 OAuth code 或支付密钥。
- 引导卡片显示“是否写入”：默认“否”；任何需要人工确认的动作单独确认。

## 11. 验收标准

### 功能验收

- 新安装、已有 binding、binding 失效、无 token、无 workspace 五种场景均能进入引导。
- 六个平台均可选择；同平台同名店铺必须要求明确选择 account_id。
- OAuth 成功、失败、过期和撤权均能正确刷新状态。
- API 超时不会显示空数据或“已完成”；重试不会重复写入。
- 引导完成后能进入真实商品目录，且展示真实 SKU、价格、库存、图片和来源。
- 生成/发布仍需要独立的事实确认、人工确认、哈希和幂等门禁。

### 宿主验收

- ChatGPT 新会话安装插件后，首句“配置大麦插件”能触发引导。
- 引导卡片中的按钮/动作能调用对应 MCP 方法并展示下一步。
- 新会话能恢复上次已完成步骤，不重复询问已确认信息。
- 用户关闭或稍后再说后，下一次仍能从当前阻断步骤继续。

### 发布门禁

- 源插件与 marketplace 镜像 byte-identical。
- `initialize`、`tools/list`、`tools/call` 契约通过。
- 引导相关 API、MCP、RLS、审计和 worker 测试通过。
- 真实 bearer/OIDC、官方 OAuth、模型中转和支付 provider 缺少证据时保持阻断。

## 12. 埋点与可观测性

记录以下非敏感事件：`onboarding_started`、`step_viewed`、`step_completed`、`step_blocked`、`step_retried`、`onboarding_resumed`、`onboarding_completed`。每条事件携带 `request_id`、`trace_id`、workspace 脱敏标识、步骤名和耗时，不记录 token、密码、商品原始图片或支付信息。

## 13. 分阶段交付

### Phase 1：引导可见性

新增 `onboarding.status` 只读聚合、首句引导卡片、进度/阻断/下一步展示；不改变现有业务权限。

### Phase 2：可恢复绑定

接入 workspace binding 恢复、平台/店铺选择、OAuth 状态刷新、重试与审计事件。

### Phase 3：首个价值闭环

引导完成后进入真实商品目录和首个只读任务；增加宿主新会话、断点恢复和错误注入验收。

### Phase 4：上线门禁

完成 marketplace 镜像、MCP/OpenAPI/RLS、真实 OAuth、模型中转和支付 provider 证据闭环后，才开放生产写能力。

## 14. 待确认决策

1. 引导是以 ChatGPT 对话卡片为主，还是同时提供一个插件内 HTML 设置页；建议对话卡片为唯一主入口，HTML 仅作为详情辅助。
2. 是否允许平台管理员预绑定工作区；建议允许，但商家仍必须明确选择店铺。
3. 无创意点时是否展示平台连接入口；建议不展示，只显示服务端授权的账单/订单恢复入口。
4. 是否将模型中转配置暴露给商家；建议不暴露，只显示“平台模型服务已配置/未配置”。
