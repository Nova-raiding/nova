# 运营后台能力闭环 PRD

## 目标

把运营后台从“多个领域查询页”升级为可审计的运营控制台：每个运营动作都有明确范围、权限、状态机、证据和失败恢复路径，消除商业、营销执行、规则治理和数据删除的信息孤岛。

## 用户与场景

- 平台运营：跨 workspace 查看异常、履约、模型成本和发布门禁。
- 客服/支持：处理工单、用户风险和数据删除申请，但不能获得平台级写权限。
- 财务运营：查看订单、点数、权益和模型用量，执行双人审批的调整。
- 发布/规则管理员：执行回填、规则发布、回滚和交付门禁检查。

## MVP 需求

### R1 运营工作项统一视图

按 `workspace_id + operation_id + trace_id` 聚合队列、API、Worker、审计、账务和资产证据；支持状态、负责人、重试次数、最后错误和下一动作。

### R2 商业控制面

统一展示权益、订单、点数账本、模型用量、服务履约和阻断原因。点数调整必须 propose → decide 双阶段，所有变更有前后快照和审计。

### R3 治理动作

支持 canonical backfill 的创建、详情、运行、暂停、恢复；支持规则审计、交付 readiness、数据删除批准/取消。所有动作必须具备幂等键和冲突版本。

### R4 营销执行与资产对账

展示生成、扫描、审核、发布、归档和计费对账；异常可分配、重试、确认或导出证据。缺少模型/扫描密钥时显示配置阻断。

### R5 权限与范围

平台 scope 与 workspace scope 强制分离；前端只消费 `ops.session` 返回的 capability projection，不从角色名推断权限；后端重复执行 capability、scope、RLS 和审计检查。

## 非目标

不把手机/平板作为验收目标；不接入未授权电商平台；支付和外部平台在测试阶段使用 mock；模型调用使用本地中转并保留真实鉴权、用量、成本和错误证据。

## 验收标准

- 18 个未被前端引用的高风险方法全部有明确页面、调用方或书面“不提供 UI”的理由。
- 关键写动作均有成功、拒绝、冲突、超时、重复提交和配置缺失测试。
- platform/workspace 两种 scope 真实 ECS 验收通过。
- 运营后台能从一个 operation_id 追到 API、Worker、审计和账务证据。
- 缺失配置 fail-closed，并显示可操作的阻断原因。

### 发布前不可省略的证据包

每个 P0/P1 操作需保留同一 `operation_id` 的请求、响应、审计、worker/outbox、账务/资产结果和失败重试证据；截图或静态代码不算替代。所有写操作还必须覆盖重复提交、版本冲突、权限拒绝和缺失配置 fail-closed。
