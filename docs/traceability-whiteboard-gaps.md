# 白板需求追溯与代码缺口审计

审计日期：2026-08-24  
审计范围：`docs/PRD-merchant-marketing-codex-final.md` 第 24 章、第 24.4 节，并对照源码、MCP 工具、API/领域测试和当前运行证据。  
审计目标：判断白板需求是否真正落地，不以 `docs/implementation-status.md` 的文字声明作为唯一证据。

> 范围校正（2026-08-26）：产品平台范围已从历史四平台修订为六个平台：京东、淘宝、天猫、拼多多、小红书、抖音。本文中“四平台”均属于历史审计措辞；当前生产 capability/canary 门禁按六个平台执行，小红书和抖音在缺少官方证据时继续保持 Conditional/Blocked。

## 1. 判定口径

| 标记 | 含义 |
|---|---|
| ✅ 已落地 | 有对应代码入口，并有针对性测试或可重复运行证据；不代表已经获得外部平台生产资格。 |
| 🟡 部分落地 | 有数据结构、接口、fixture 或局部流程，但没有覆盖 PRD 的完整验收条件。 |
| ❌ 未落地 | 未找到可调用实现，或当前实现不能满足 PRD 定义。 |
| 🔒 外部门禁 | 代码可能存在，但必须用真实平台、云环境、模型或供应商证据验证；本地测试不能签署完成。 |

本次审计特别区分三种状态：

1. “代码存在”不等于“用户流程完成”。
2. “fixture/模拟成功”不等于“京东、淘宝/天猫、拼多多生产可用”。
3. “单元/API 测试通过”不等于“Codex App、真实授权、真实回读和云容量通过”。

## 2. 总结结论

当前项目已经形成一个可演示、可测试的 Codex Plugin 工作流骨架：工作区、品牌/素材、商品/SKU、规则、任务、创意方向、内容版本、审核、导出和发布门禁均有代码入口；第24.1与第24.2的大部分 P0 业务骨架也有测试覆盖。

但还不能宣布“白板需求全部完成”或“可直接给商家生产使用”。当前最重要的缺口不是再增加一个演示工具，而是把以下证据补齐：

- 四个平台四个 schema profile 的真实 OAuth、读取、全量/增量同步、创建/更新、状态查询和撤权 canary。
- 真实云环境的 50 家首发容量，以及向 500 家目标扩容的 6 小时稳定性、公平性和故障恢复报告。
- 真实模型/图片服务、对象存储、文件扫描/OCR 和生产支付/凭证配置。
- 运营告警、数据导出/删除、任务时间线重建和 Codex App 真实界面的回归证据。
- 第24.4登记的 P1/P2 视觉、促销、批量和自动化能力目前大多是 Brief 或接口预留，不是最终生产能力。

## 6. 明确的 P0 漏项

下面是本轮确认的 P0 漏项或 P0 证据缺口。它们不是“以后体验优化”，而是影响 PRD 的生产验收、上线或商家真实性承诺。

### P0-01：四平台真实能力未完成生产验收（发布阻断）

代码有四个平台 profile、HTTP connector、签名/映射、fake connector、readiness 和 capability-evidence gate；测试主要证明 contract、fixture 和 fail-closed。当前未提供四个平台各自的官方应用、scope、测试店铺、真实 OAuth verifier、全量/增量同步、创建/更新、查询状态、撤权和回读证据。

涉及代码/证据：`packages/connectors/src/platform-preflight.ts`、`packages/connectors/src/canary.ts`、`tests/capability-evidence-gate.test.ts`、`docs/implementation-status.md`“尚未宣称完成的生产门禁”。

验收要求：JD、Taobao、Tmall、Pinduoduo 每个 profile 的 8 项能力达到 `production_canary`；任何一个 profile 未达到，只能显示 `Conditional/Blocked`，不能显示生产可用。

### P0-02：50/500 容量没有真实云门禁（上线阻断）

已有本地/Compose 容量烟测和 `cloud_gate` 校验器，但现有运行证据明确标记 `cloudGate=false`。尚未完成真实预发布云环境的 50 家 profile、30/60 RPS、50 作业突发、6 小时稳定性，以及 100/250/500 波次扩容报告。

涉及证据：`tests/http-capacity-gate.ts`、`tests/capacity-evidence-gate.ts`、`docs/implementation-status.md`。本地 loopback/Compose 结果不能替代云门禁。

### P0-03：生产 AI/图片服务没有可验收的真实供应商证据

代码支持 OpenAI-compatible provider 和 fixture fallback，并且主图/Brief 工具能返回结果；但未配置真实生产模型时必须 fail-closed，fixture 不能视为真实商品图质量或生成服务已完成。真实图像生成还需要验证主体保真、尺寸、清晰度、OCR、无水印/Logo 约束、成本、超时和配额。

涉及代码：`packages/ai/src/image-generator.ts`、`packages/ai/src/generator.ts`、`packages/application/src/service.ts`。

### P0-04：素材安全解析能力不完整

上传 allowlist、签名校验、隔离区、扫描晋级和文本类 PDF/DOCX/XLSX/CSV/TXT 解析已经存在；`asset.facts.confirm` 已补齐“自动解析失败后由商家在 Codex 内人工补录”的闭环，并独立记录 `manual` 来源、确认人、确认时间和原因，不伪装为 OCR 成功。图片 OCR、扫描 PDF 和 AI/EPS 的真实外部解析器仍未接入，因此自动提取能力继续为 Conditional。

涉及代码：`packages/application/src/document-parser.ts`、`apps/api/src/server.ts` 的 `asset.parse`/`asset.facts.confirm`、`apps/api/src/asset-parse.e2e.test.ts`。

### P0-05：运营可观测性仍缺生产观测验收

`workspace.metrics` 已能返回部分商品风险和任务漏斗；现已补齐工作区隔离的授权失效、同步失败、发布拒绝/未知、任务失败和内容 P0 阻断告警，支持运营角色确认、审计和 `ops.audit.export` 导出，并由运营台展示。告警统一通过 `OPS_ALERT_WEBHOOK_URL` / `OPS_ALERT_WEBHOOK_SECRET` 投递，使用 HTTPS、HMAC、3 秒超时和 429/5xx 重试；未配置或生产使用 HTTP 时 fail-closed。仍需在真实环境证明通知到达、成本/模型供应商明细和仅凭 task ID 的跨系统生产链路重建，不能将本地告警数据当作外部观测平台验收。

### P0-06：数据生命周期/删除和生产对象存储尚无完整验收

对象存储接口、KMS/配置门禁、生命周期配置校验、删除申请接口/运营台和删除 Runbook 已存在；但真实云 bucket、扫描回调、签名下载、90 天保留、7 天删除宽限、30 天备份轮转和跨系统删除证明尚未完成。商家真实素材上线前仍必须完成这些外部演练，否则 FR-05 和安全/隐私章节只能算 Conditional。

### P0-07：Codex App 主界面验收证据不完整

MCP bridge 和安装 smoke 已通过，部分可见 Codex App 演示也完成过；但 PRD要求对话是 P0 主界面，所有 P0 流程要能在键盘/纯文本完成，并验证弱网、断网、刷新、切换会话、可访问状态播报和图片/交付物真实展示。当前测试库存以 API、bridge 和 Merchant Studio 为主，缺少稳定、自动化、可重复的 Codex App UI E2E 报告。

| 多品牌协作/复杂角色审批 | ❌ 未落地 | 当前是工作区级权限和规则管理员边界，没有完整编辑者/确认者分离、多品牌协作和审批流。 |

## 9. 建议的下一轮执行顺序

### 阶段 A：先关闭 P0 发布阻断

1. 建立四个平台四 profile 的真实 capability evidence 表；每项能力附官方请求/响应、测试店铺、scope、时间和签署人。
2. 在同版本预发布云环境完成 50 家容量合同；再按 100/250/500 波次复测，不用本地结果替代。
3. 配置并验证生产模型、图片模型、对象存储、KMS、扫描/OCR、Vault、告警和支付回调；所有未配置路径保持 fail-closed。
4. 增加 Codex App 黑盒回归：安装、健康检查、素材上传/阅读、商品同步、事实确认、任务、内容、主图展示、审核、版本、导出、发布预检；记录截图和失败重现步骤。
5. 增加 P0 黄金任务集，至少覆盖：错 SKU、过期价格、未授权素材、规则过期、Token 撤回、同步部分失败、发布驳回、发布 unknown、重复确认、跨工作区访问。

### 阶段 B：先做最有业务价值的 P1

1. 先做促销/价格快照，因为它直接影响发布风险。
2. 再做真实商品图保真编辑和多尺寸导出，解决当前用户最明显的价值问题。
3. 再做多商品 Banner/批量平台适配；每个子任务独立规则、版本、审核和发布。
4. 最后做广告/视频 Brief 的真实规格适配，不提前承诺投放和成片。

### 阶段 C：P2 单独立项

视频渲染、数字人、无人值守发布、自动规则采集和协作审批都需要单独的子 PRD、权限模型、供应商评估、成本预算和回滚方案，不建议混入当前 P0/P1 修补。
