## Pass 1：信息架构，7/10 → 建议修订后 9/10

§7 规定表单步骤，§12–13 已分开商家与运营动作，但没有决定入口、列表首要列和目录版本并存时看哪项。若前端照搬当前最高版本列表，运营创建草稿后会误以为在售商品消失，商业状态也难解释。D1（P1）：将“商品当前销售状态”和“编辑版本审批状态”分列，当前销售快照固定可见，草稿放版本抽屉；区分“下架”“归档”，不要再用“删除 / 停售”作为同一个动作。

建议 IA：

```text
平台财务中心
├─ 商品目录 [套餐 | 权益包 | 开通费]
│  ├─ 搜索/状态筛选 → 商品表：名称 / 售价·周期 / 销售状态 / 编辑版本状态 / 操作

│       └─ 编辑四步 → 保存草稿 → 审批 → 发布预览 → 确认上架

├─ 我的套餐 [当前已生效 | 已付未来待生效 | 权益包 | 订单历史]
│  └─ 升级 → 差价报价 → 确认支付 → 订单状态 → 权益结果
```

首屏只能显示三项时：Ops 显示目标商品/价格与周期/销售与编辑状态；商家显示当前档位与到期、开通资格、本次可执行动作。版本代码、审计标识放次级详情及复制入口，金额和企业身份不可折叠。复用现有导航，不强制重做整个财务中心；新增页签与可直达详情链接即可。

PRD 已定义 409 保留表单、支付异常和部分合款，但没有定义这些状态呈现在什么位置、是否可继续点击购买。最危险的遗漏是响应丢失后让运营重新建单/再次分配，以及把“已到账”绿勾解释成已生效。D2（P1）：加入以下用户可见状态表，提交后采用订单状态页，查询失败与真正空记录分开；金额/资格过期快照只读并禁用新付款提交。

| 功能 | 加载中 | 空状态 | 失败 | 成功 | 部分/未知 |
|---|---|---|---|---|---|
| Ops 商品表 | 表头保留、行骨架、“正在读取目录” | 真空：“尚无商品”，有权者“新增草稿”；搜索空：“没有匹配商品/清除筛选” | 行内错误+重试；旧数据注明读取时间、不可据此发布 | 当前销售与草稿分别显示 | 局部版本读取失败明确“版本历史暂不可用”，不伪造无草稿 |

| 商家通知 | “正在读取通知” | “暂无商品与购买消息”，仍可去购买中心 | 通知错误+重试，风险提醒独立可用 | 未读、已读及详情入口 | 商品已下架/失去可见性禁购买；不泄露私有商品详情 |
| 购买中心 | 商品比较骨架，提交禁用 | “暂无可购买商品”，查看我的套餐 | 目录不可用不可购买；保留已购查询入口 | 展示生效价、周期、开通与首期分项 | 商品政策未就绪显示可读阻断原因，不能默认价格为 0 |
| 我的套餐 | 状态未确认，不能假装未购买 | 确认无当前套餐：“购买套餐”；已开通资格单列 | “暂无法确认套餐”，重试并保留更新时间标记 | 当前权益及未来账期各自起止、来源 | “已支付待授予/待处置”有订单入口；不可混入当前已生效 |
| 升级报价 | “正在计算差价”，支付禁用 | 无有效套餐引导新购，同级引导续购 | 源版本变化/跨周期/下架显示原因和重新报价 | 明细、截止、补差价、到期不变，明确“确认支付 ¥X” | 支付处理中可查单；核验延迟/已收款待处置显示保留的到账事实与负责人，禁重付 |
| Ops 客户选择 | 搜索加载，建单禁用 | 查无用户：“创建账号并邀请”；多企业必选 | 无授权显示拒绝，不展示其他企业订单 | 企业+客户+资格+当前/未来套餐确认 | 账号已建但未开通显示仅可登录处理支付 |
| 人工收款与分配 | 核验中不重复提交 | 无收款：“登记并核验真实收款”；不默认当前时间 | 不足/币种不符/证据缺失显示具体金额差与字段 | 每条明细分别显示到账、依赖、授予；结果可追溯 | “套餐款已分配，待开通款” / “开通已完成，套餐差 ¥X”；多付余额待处置；每企业各自结果 |

## Pass 3：用户旅程与情绪，7/10 → 建议修订后 9/10

金额、赠点与不重收开通费的解释已经清楚，但当前用户可能仍在点数购买弹窗里看到含糊的“月度套餐”并误把开通赠点算成月套餐额度。付款后等待核验是最长的不安窗口，需要订单状态持续承担解释，不只是 toast。D3（P1）：升级/首购确认和已购页增加明细及时间语义；所有时间面向用户按亚洲/上海完整日期时间显示，服务端 UTC 计算，剩余时间为辅助，不仅显示整数剩余天数。

| 步骤 | 用户行为 | 情绪 | 必须显示的支持 |
|---|---|---|---|
| 1 | 首次进入财务页 | 想确认能否使用 | 企业名称、开通状态、当前生效档位和到期，先于目录营销 |
| 2 | 比较套餐与包 | 担心买错或买重 | 按权益行的三档比较表、同单位额度；独立包标适用套餐/有效期/叠加上限 |
| 3 | 确认首购 | 对额外费用敏感 | 开通费与首期月费两条金额、总计；6×500赠点独立说明，费用不抵扣 |
| 4 | 确认升级 | 担心全价再收一次 | 当前成交周期价、目标周期价、起止、计算时点、剩余比例、差价、权益增量、到期不变 |
| 5 | 支付/转账 | 付款后不确定 | 应付与到账分开，订单号/查单，支付成功后仍可能待授予；避免“已完成”泛称 |
| 6 | 等待人工核验 | 焦虑并可能重付 | 最后查询时间、正在核验/待依赖/待处置原因，继续查原单，不要求再次付款 |
| 7 | 查看结果与未来账期 | 需要信任 | 生效档位和时间、创意点分来源、原到期保留、未来已付套餐保持原合同 |
| 8 | Ops 遇不足/多付 | 怕处理错钱 | 收款实际额、已分配、未分配、差额、目标企业、负责人及下一步；每条状态独立 |

5 秒：看懂“我是谁、已购什么、现在能做什么”。5 分钟：可完成选商品、核对明细、建单并重新找到订单；转账到账/人工核验不伪造 5 分钟承诺。5 年：历史合同、调整原因、原收款和授予证据可追溯，运营改价后旧单仍按旧价解释，避免长期信任流失。

报价确认采用一个表格：当前套餐/周期成交价，目标套餐/周期价，原账期起止，计算时间及剩余比例，应补金额，新增权益与到期。报价接受截止与成功到账截止分别标名；本期二者可相同，但不能把点击支付视为成功到账；上海时间显示到分钟/秒，后端 UTC 时点仍为依据。临近截止提示“须在 X 前成功到账；核验晚于原到期可能进入待处置”，不保证银行延迟；报价过期禁发起新支付，重新报价需再次确认金额。

## Pass 5：设计系统对齐，6/10 → 建议修订后 9/10

## Pass 6：桌面适配与可访问，5/10 → 建议修订后 9/10

项目宪法明确桌面工作台，手机和平板响应要求不适用，不能套用 skill 的移动建议成为阻断。当前 PRD 的桌面浏览器验收不等于键盘/屏幕阅读器已经有可实施的标准。D6（P1）：建立桌面缩放与键盘契约；1440×900 100% 和 200% 缩放金额、企业和确认操作可阅读可操作，宽表在局部横滚并固定名称/金额关键列，页级不横滚，抽屉和确认区不得超屏丢动作。

所有功能/权益行应有持久标签和规范单位，不只 placeholder；添加/移除一行说明目标，移除后焦点到相邻行。可访问 landmark 为 nav/main，页签有选中语义，表格用真实表头及可读状态文本，checkbox/数值框关联字段标签与错误。打开 Drawer/Modal 限制焦点在内部，Esc 可退出非提交过程，关闭后回原触发按钮；危险核验确认默认聚焦取消，提交 busy 期间不重复执行，终态后聚焦结果标题。

键盘顺序按企业→商品→明细→确认，不先落入审计技术字段。状态更新用 `role=status/aria-live=polite`，字段/提交失败 `role=alert`，报价倒计时不每秒播报；更改或过期仅播报一次。正文及重要辅助信息≥16px、对比≥4.5:1，控件和 focus 与邻色≥3:1，动作命中面积至少44×44px；状态不可仅依颜色，普通详情链接 visited 应有可区别样式。实际对比、长中文名、合并转账行/大量权益行及屏幕阅读器顺序须实现后桌面验收，此报告不伪造完成。

| 在售与草稿关系 | 新草稿覆盖在售显示 | 当前销售与编辑状态分列，历史抽屉 |
| 报价与到账时间 | 点击支付被当成功、晚核验误报失败 | 分列计算/接受/到账截止及待处置状态 |
| 当前/未来合约 | 当前升级后未来低档消失或被改价 | 各自列起止/版本与“未来待生效” |
| 收款分配操作 | 原始技术字段让 Ops 填错事实 | 选择客户→订单→收款事实→分配表→确认结果 |
| 失败与响应未知 | 重付、重建、重复开通 | 保留输入，按原标识查结果再重试 |
| 桌面可访问 | 小字、焦点丢失、状态只靠颜色 | 上述局部字号/键盘/缩放契约 |

## 可直接纳入 PRD 的最小补丁

建议扩展 §7（或新增 §15 详细交互），不修改已确认的业务价格、期限、赠点或支付规则：

1. Ops 商品目录采用套餐/权益包/开通费页签与表格；名称、价格·周期、当前销售状态、最新编辑版本审批状态分别展示；新草稿不隐藏当前在售。下架与归档独立操作，版本历史抽屉显示差异及审计。
2. 商家“我的套餐”优先当前生效合同，未来已付待生效合约另区显示，权益包分来源及有效期；购买中心为权益行三档比较表和独立售卖包表；已到账待授予/待处置显示订单状态，不能显示成已购生效。
3. 首购确认显示开通费、首期费、总计以及独立赠点计划；升级确认显示当前成交周期价、目标周期价、原起止、计算时点、剩余比例、差价、权益增量及到期不变；分列报价接受截止和成功到账截止，上海时区显示完整时间、后端 UTC 计算。临近/超期以业务文案提示并禁新支付，不把发起支付当成功。
4. Ops 代购以目标企业确认→商品明细→收款登记核验→分配表→确认结果分步；分配表列订单应付、累计分配、本次分配、剩余应付、依赖和授予状态；顶部列实收、未分配余额、客户及企业。nonce/hash/provider event 等内部技术字段由服务生成/读取放审计详情，不要求普通运营手填；真实银行流水、到账金额/时间和证据引用仍需核实输入，不能代为编造。
5. 纳入本报告 Pass 2 状态表；每条明细呈现自己的成功/待依赖/不足/待处置，部分到账不显示整批完成；响应未知先查同一请求/订单结果，409 保留输入及差异确认后再提交；查询错误不等同空目录或未购买。
6. 复用现有主题组件/本地字体，不引入远程字体；本功能正文与表单/权益金额文字≥16px、正文对比≥4.5:1、动作44px、状态文字与颜色并用、focus可见；持久标签、金额右对齐等宽数字、表头语义、Modal焦点管理与适度 live-region；1440×900及200%桌面缩放验收，不增手机/平板门禁。

## 错误与救援

报价变化/过期：展示旧报价原因，不静默改应付；重新报价显式再确认。人工核验冲突：保留真实收款事实、刷新可分配余额，旧输入仍可查看，不直接再次核验。跨企业/无权限：拒绝目标操作，不展示不授权客户；回授权客户选择页。

目录/网络读失败：显示最后读取时间，禁需要最新事实的写入，保留订单查单。收款已提交但响应丢失：按幂等键查原结果；按钮显示“确认结果中”而非新的确认核验。已经收款待处置：明确原因、当前负责人和处理期限；处理记录与联系入口可见，不提示用户重复付款。

## 不在范围内

- 手机/平板布局：项目明确只有桌面工作台。
- 整站视觉系统、字体更换、全局小字号迁移：本期限定商业流程的可读性及组件复用。
- AI 图片/品牌重做/多风格变体：designer不可用，且当前任务是需求评审。
- 新折扣、免费商品、钱包、自动降级或重算未来已付合同：不属于已授权业务规则。
