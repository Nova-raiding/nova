# 六平台人工运营替代操作手册

适用平台：京东、淘宝、天猫、拼多多、小红书、抖音。

适用场景：Store Nova 暂时无法取得平台官方 OAuth/API 授权，由运营人员负责获取商品资料、维护商品事实，并登录平台商家后台完成最终发布。

## 1. 运营边界

人工模式可以完成商品资料导入、内容生成、审核、交付包导出和人工发布，但不能提供自动同步、自动发布或可信 API 回执。

必须遵守以下原则：

- 不向商家索取平台密码、Cookie、短信验证码、access token 或浏览器会话。
- 不把运营人员浏览器 Cookie 导入 Store Nova。
- 不绕过登录墙、验证码、风控或平台访问限制。
- 不把截图、口头确认或人工登记伪装成平台 API 回执。
- 不确认的价格、材质、功效、资质和库存不得交给模型猜测。
- 每次操作必须绑定正确的商家工作区、平台和店铺。

## 2. 角色与职责

| 角色 | 职责 |
|---|---|
| 商家联系人 | 提供商品资料、原图、资质、店铺范围并确认商品事实 |
| 资料运营 | 收集文件，执行导入，处理缺失字段 |
| 内容运营 | 发起文案、图片或视频生成，检查平台适配结果 |
| 审核人员 | 核对事实、平台规则、版权和最终版本 |
| 发布人员 | 登录商家后台，手动创建或更新商品/内容 |
| 复核人员 | 核对线上结果与批准版本，登记证据和异常 |

同一个人可以承担多个角色，但高风险商品、批量发布和重大修改建议由另一人复核。

## 3. 开始前检查

为每个商家建立一张运营任务单，并填写：

- 商家名称和 Store Nova 工作区；
- 目标平台和店铺名称；
- 平台店铺 ID 或商家可识别的店铺编号；
- 本批商品数量；
- 操作类型：新建、更新、仅生成内容或仅导入资料；
- 交付截止时间；
- 商家联系人和运营负责人；
- 是否涉及功效、食品、医疗、母婴等高风险声明。

确认 Store Nova 当前工作区后再上传文件。不得仅凭商品名称判断工作区。

## 4. 向商家收集资料

优先让商家提供 Excel/CSV 模板。最低字段如下：

| 字段 | 是否必填 | 说明 |
|---|---:|---|
| platform | 是 | `jd`、`taobao`、`tmall`、`pinduoduo`、`xiaohongshu` 或 `douyin` |
| account_id | 是 | Store Nova 中登记的店铺范围。没有时由**平台运营**通过 MCP 方法 `ops.platform.store.record.create`（平台运营专用，商家工具面不可见；必填参数 `workspace_id`、`platform`、`account_id`、`reason`）为该商家登记人工店铺记录，再导入本表资料。该方法只写 `platform_accounts` 的 `token_state=manually_registered`，不写任何凭据、scope 或平台回执，也不会把记录标成已授权。**该方法需要目标环境已部署提供它的上线版本**；在部署到该版本之前，运营不得绕过它直接改数据库、复用其他商家的 account_id 或把人工数据当成已授权店铺使用，只能先收集资料并等该方法可用后再登记 |
| 商品货号 | 是 | 商家内部稳定编号，不能只用商品标题 |
| 商品名称 | 是 | 不包含未经确认的营销承诺 |
| 类目 | 是 | 使用商家确认的平台类目 |
| SKU 编码 | 有 SKU 时必填 | 每个规格使用稳定且唯一的编码 |
| 颜色/尺码/型号 | 按商品填写 | 不同 SKU 不得混用 |
| 价格 | 是 | 标明是否为日常价、活动价或建议价 |
| 库存/供货状态 | 是 | 人工导入只是时间点快照 |
| 材质、成分、参数 | 按商品填写 | 必须有包装、说明书或商家确认作为来源 |
| 商品原图 | 推荐 | 使用文件或可下载链接，并确认商用权益 |
| 宣传限制和资质 | 高风险商品必填 | 例如检测报告、授权书、禁用词要求 |

可接受的来源：

1. 商家导出的 Excel、CSV 或 JSON；
2. 商家提供的图片、PDF、Word、说明书和资质文件；
3. 无需登录即可访问的公开商品页面；
4. 商家书面确认的人工补录内容。

公开页面出现登录、验证码或风控时立即停止，改请商家提供导出表、PDF、截图或资料包。

## 5. 文件检查和导入

1. 检查文件是否属于当前商家和当前店铺。
2. 删除与任务无关的消费者信息、订单信息和个人信息。
3. 检查表格公式、隐藏列、合并单元格和重复行。
4. 在运营后台上传文件，等待安全扫描完成。
5. 打开导入预览，逐行处理以下错误：
   - 平台值无效；
   - 商品标题为空；
   - 同一商品重复；
   - 相同商品货号对应不同标题；
   - 价格或库存为负数；
   - SKU 编码重复；
   - 图片或资料无法确定归属。
6. 确认预览后执行批量导入。
7. 记录导入文件名、文件哈希、操作者、导入时间、成功数和失败数。

导入失败时不得直接在生产数据库中修改记录。修正源文件后重新预览和导入。

## 6. 商品事实确认

导入完成不等于事实已经确认。运营人员必须逐商品核对：

- 商品、SKU 和图片是否对应；
- 价格的含义和有效时间；
- 材质、成分、尺寸和技术参数；
- 功效或性能声明是否有依据；
- 品牌名、授权关系和素材权益；
- 平台和店铺范围是否正确。

事实来源标记：

- `商家文件`：来源于商家提供的表格或资料；
- `公开页面`：来源于可公开访问的页面，并保留 URL 和访问时间；
- `人工确认`：由商家或授权运营人员书面确认；
- `未知`：缺少依据，不得用于事实性文案。

## 7. 生成和审核内容

1. 在 ChatGPT 中选择 Store Nova 插件。
2. 选择正确工作区、平台、店铺和商品。
3. 明确目标，例如商品详情、主图文案、小红书笔记或抖音视频脚本。
4. 检查插件引用的商品事实是否属于当前商品和 SKU。
5. 生成候选内容。
6. 内容运营检查事实、语气、格式和平台适配。
7. 审核人员检查禁用词、夸大宣传、版权、资质和价格有效性。
8. 修改后生成新版本，不覆盖历史批准版本。
9. 对最终版本执行人工批准。

任何缺少依据的内容都应删除或改为非事实性表达，不能用“可能”“一般”等词掩盖事实缺失。

## 8. 导出人工发布包

批准后导出 Markdown、JSON 或 bundle。发布包至少应包含：

- 最终标题和正文；
- 平台和店铺范围；
- 商品及 SKU 对应关系；
- 图片、视频或素材清单；
- 已确认事实及来源；
- 审核结果；
- 版本号和生成时间；
- 文件 manifest 与 SHA-256。

没有平台真实回执时，发布包不得包含伪造的 `publish-receipt.json`。

## 9. 人工登录平台并发布

发布人员在受控办公设备上完成：

1. 使用商家自行管理的平台账号登录官方商家后台。
2. 核对店铺名称和账号，避免发布到同平台的错误店铺。
3. 根据批准版本新建或编辑商品/内容。
4. 按 SKU 上传对应图片并填写规格、价格和库存。
5. 上传批准的视频、主图和详情素材。
6. 在提交前逐字段对照交付包。
7. 保存平台预览或草稿。
8. 由复核人员检查预览。
9. 获得允许后点击平台提交或发布。
10. 记录平台返回的商品 ID、内容 ID、页面 URL、发布时间和平台状态。

不要把平台后台密码或验证码复制到 Store Nova、ChatGPT、工单或审计备注中。

## 10. 回填结果

人工发布后，在 Store Nova 记录：

- 工作区、平台、店铺和商品；
- 对应批准版本和交付包哈希；
- 发布人员和复核人员；
- 操作时间；
- 平台商品/内容 ID；
- 可访问的公开 URL；
- 平台显示状态；
- 截图或平台导出文件的私有资产引用；
- 差异说明和异常记录。

状态必须使用以下含义：

| 状态 | 含义 |
|---|---|
| `export_ready` | 已生成交付包，尚未发布 |
| `manual_publish_in_progress` | 运营人员正在平台后台操作 |
| `manual_publish_reported` | 人工报告已提交或发布，尚无 API 验证 |
| `manual_review_required` | 平台驳回、结果不明或线上内容存在差异 |
| `platform_verified` | 仅在未来获得官方 API 的真实远端回执后使用 |

人工发布不得直接写成 `platform_verified` 或自动化 `published`。

## 11. 发布后复核

发布后由不同人员完成复核：

1. 打开公开商品或内容页面；需要登录才能查看时，在平台后台复核。
2. 对照批准版本检查标题、正文、SKU、价格、图片和视频。
3. 检查平台是否自动裁剪图片、过滤文字或修改格式。
4. 检查链接和商品 ID 是否属于正确店铺。
5. 记录差异。
6. 无差异时将任务保持为 `manual_publish_reported` 并标记“人工复核完成”。
7. 有差异时进入 `manual_review_required`，修订后重新审核和发布。

## 12. 日常更新

- 价格、库存和上下架状态由商家或运营按约定周期重新导出并导入。
- 不得把上一次导入的库存当成实时库存。
- 商品事实发生变化后，旧的内容批准和发布确认应重新检查。
- 涉及材质、功效、资质或 SKU 图片变化时必须重新审核。
- 建议每日维护变更清单，每周抽查已发布商品。

## 13. 异常处理

| 异常 | 处理方式 |
|---|---|
| 文件安全扫描失败 | 隔离文件，请商家重新导出；不得绕过扫描 |
| 表格无法解析 | 转为标准 XLSX/CSV 后重新上传 |
| 商品字段冲突 | 暂停生成，请商家确认唯一事实 |
| 图片与 SKU 不匹配 | 暂停发布，重新绑定素材 |
| 平台要求验证码 | 由商家或授权发布人员在官方页面处理，不记录验证码 |
| 平台驳回 | 保存错误码/截图，修订内容后重新审核 |
| 提交后状态不明 | 标记 `manual_review_required`，不要重复提交 |
| 发布到错误店铺 | 立即停止后续操作，登记事故并由授权人员回滚 |
| 线上内容与批准版本不一致 | 保留差异证据，重新生成或手动修正并复核 |

## 14. 每日交接清单

每个运营班次结束前确认：

- [ ] 所有操作均在正确工作区和店铺范围内；
- [ ] 原始文件已完成安全扫描；
- [ ] 商品事实缺失项已标记，没有模型猜测；
- [ ] 最终内容已有明确版本和人工批准；
- [ ] 人工发布记录绑定到对应交付包哈希；
- [ ] 没有把人工截图标记为 API 回执；
- [ ] 状态不明、平台驳回和差异项已进入异常队列；
- [ ] 没有在系统中保存密码、Cookie、验证码或 token；
- [ ] 下一班次能够根据记录继续处理。

## 15. 质量指标

建议按周统计：

- 导入成功率和字段缺失率；
- 首次审核通过率；
- 每件商品人工处理时长；
- 发布错误店铺次数；
- SKU/图片不匹配次数；
- 平台驳回率；
- 发布后差异率；
- 状态不明超过 24 小时的任务数量；
- 单人每日安全处理上限。

当错误率上升或人工积压持续增加时，应降低接单量、增加复核人员，或优先推进对应平台的官方 API 接入。

## 16. 一页式标准流程

```text
接单并确认工作区
  → 收集最小商品资料
  → 删除无关个人数据
  → 上传并通过安全扫描
  → 预览和确认导入
  → 核对商品事实与素材权益
  → 生成平台内容
  → 人工审核并批准版本
  → 导出带哈希的交付包
  → 运营登录官方商家后台
  → 双人复核后提交
  → 回填人工发布证据
  → 线上复核和异常处理
```
