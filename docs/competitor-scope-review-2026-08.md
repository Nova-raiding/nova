# 竞品范围评审：四类 P0 能力

日期：2026-08-24  
适用基线：`docs/PRD-merchant-marketing-codex-final.md` v1.4 Final  以及白板需求追踪矩阵  
评审范围：多平台授权同步、商品详情/主图、规则/审核、用户确认后发布  
资料口径：只采用产品厂商或平台官方页面、官方开发者文档和官方帮助中心。  

## 1. 先给结论

本项目不应与单一“AI 作图工具”或单一电商后台正面比较，而应保持 PRD 已冻结的组合定位：

> 在 Codex App 内，把商家的官方店铺数据、商品事实、素材权益、平台规则、内容产物和用户确认后的发布动作串成一条可追溯工作流。

官方资料显示，竞品和平台各自把某一个环节做得较深：

- 美图设计室的优势是商品原图参考、白底/场景/多角度和批量商品图。
- Shopify Sidekick 的优势是管理员内自然语言、任务清单、内容生成和权限约束。
- 淘宝、京东、拼多多开放平台的优势是官方授权后的商品数据和平台写入能力，但接口权限、类目 schema、资质和平台审核均由各平台控制。

因此，本项目在现有 PRD 范围内的最佳方案不是继续扩展更多生成类型，而是把四类 P0 能力做成一个“证据优先、确认后写入”的商品任务闭环：

```text
官方授权
  → 平台能力探测
  → 商品/SKU/价格/库存/图片同步
  → 事实与素材权益确认
  → 平台/品类规则加载
  → 详情文案与静态素材 Brief / 主图引用产物
  → 确定性审核 + 风险提示
  → 字段差异预览
  → 用户二次确认
  → 创建/更新商品
  → 平台回执与状态对账
```

这条链路完全落在 PRD P0；不新增视频、广告、无人值守、定时发布或多商品任务。

|---|---|---|---|

## 3. 四类能力逐项评审

### 3.1 多平台授权与同步

#### 官方能力观察

淘宝官方授权文档说明：第三方应用先引导商家登录并授权，再通过授权码换取 Access Token/SessionKey；授权与账号绑定，令牌有有效期，Web 授权适合服务多商家场景。淘宝官方商品 API 目录同时列出了商品读取、批量获取、SKU、图片、商品新增/更新和天猫 schema/资质接口。

京东官方资料说明：API 调用需要与京东服务器交互，查询和修改操作在 HTTP 方法上有明确区分；京东开发者中心说明授权登录基于 OAuth2.0，且存在注册、创建应用、开发测试、发布上线的完整流程。

拼多多官方开放平台把“开发者认证 → 创建应用/服务 → 发布到服务市场”列为接入路径，并明确提供 API 文档和消息文档。这里能证明平台具备官方接入机制，但不能证明任何第三方应用默认拥有商品写权限。

#### 对现有 PRD 的最佳落地

保留 `PlatformConnector` 统一契约，但把每个平台拆成独立的四层证据：

| 层级 | 必须记录 | 验收结果 |
|---|---|---|
| 授权 | 平台、应用、店铺账号、授权时间、过期时间、scope、撤权状态 | `authorized` / `expired` / `revoked` / `reauthorization_required` |
| 读取 | 商品、SKU、价格、库存、图片、上下架状态、分页游标或增量标记 | 形成平台独立商品快照 |
| 能力 | 可读字段、可写字段、类目/资质/schema、限流和异步回执能力 | `readiness`，不能只显示“已连接” |
| 写入 | 创建/更新请求、幂等键、远端 ID、回执、对账结果 | `accepted` / `published` / `rejected` / `unknown` |

三类平台、四个 profile（京东、淘宝、天猫、拼多多）必须分别验收。跨平台同款只能共享用户明确确认的原始事实，不共享价格、规则结论、远端 ID 或发布状态。

#### 当前项目必须优先修正的点

1. 授权页不能只展示“已连接”，要展示平台、店铺、授权范围、有效期和可执行能力。
2. 同步必须保存原始平台快照、归一化快照、同步时间和来源字段，支持失败恢复和增量同步。
3. 读权限与写权限分开显示；只有读权限时，发布按钮必须阻断并说明原因。
4. 真实平台测试前不得把 fixture connector 标记为生产 ready。
5. 四个平台必须分别准备测试账号/测试店铺或官方沙箱；没有官方测试账号时，记录“外部门禁”，不能用商家生产账号冒充测试环境。

### 3.2 商品详情与主图

#### 官方能力观察

美图官方资料把“商品原图”作为输入，提供参考图、自定义场景、白底图、多角度和批量商品图，并给出主体比例、透视、边缘清晰和光影融合等质量标准。

Shopify 官方帮助资料显示，Sidekick 可以根据自然语言生成商品描述和图片，也可以使用用户上传的参考图；在图片明确保存前，图片保持私有，不自动进入店铺媒体库。官方还强调 AI 输出需要用户复核。

淘宝官方商品 API 资料则表明，商品新增/更新、主图、非主图、属性图、SKU 和平台 schema 是不同的接口或能力项，不能把“能改商品标题”理解成“能完整替换所有图片和规格”。

#### 对现有 PRD 的最佳落地

严格保留 PRD 的边界：

- P0：上传、引用、预览、裁切建议、真实商品图保护、静态素材 Brief/文案。
- P0：商品详情页结构和文案，事实字段必须绑定来源和 SKU。
- P0：主图审核只做确定性检查、风险提示和人工确认，不承诺平台最终视觉审核通过。
- P1：真实商品图背景合成，不作为当前 P0 验收条件。

建议把 Codex App 中的结果统一成“商品交付包”，用户只看到：

1. 商品事实摘要和来源。
2. 已引用素材及权益/扫描状态。
3. 详情页结构与文案。
4. 主图/静态素材引用、预览或 Brief。
5. 审核结论、阻断原因和修复建议。
6. 版本、差异和下一步动作。

图像产物必须明确标注“真实商品原图引用”“处理后商品图”或“演示概念图”，避免把 fixture 或概念图误认为真实商品主图。

### 3.3 规则与审核

#### 官方能力观察

淘宝官方 API 目录包含类目提示、商品资质校验、资质 schema、品牌类目控制和天猫商品发布/编辑 schema。这说明平台规则和字段约束具有类目、平台、商品类型和资质维度。

京东官方资料说明平台 API 与开发者流程由平台控制；京东相关官方规则资料也明确商品发布受平台规范约束。拼多多官方开放平台提供平台规范、API 文档和消息文档入口。

这些官方资料支持“平台预检必须存在”，但不支持第三方工具声称“本地审核等于平台审核通过”。

#### 对现有 PRD 的最佳落地

审核分为三层，保持现有 FR-10，不增加新需求：

| 层级 | 检查内容 | 结果语义 |
|---|---|---|
| 确定性检查 | 必填字段、SKU/价格/库存一致性、图片格式/尺寸、禁用词、素材权益和规则有效期 | 可阻断，返回 P0/P1/P2、来源、规则版本和修复建议 |
| 平台预检 | 平台字段映射、类目 schema、资质字段、当前授权 scope、远端能力 | 预检通过不等于平台最终审核通过 |
| 外部结果 | 平台真实受理、驳回、审核中、发布状态和错误码 | 以平台回执和对账为准 |

规则中心必须保存：来源、规则版本、scope、有效期、核验时间、严重度、动作和命中证据。用户不能用自然语言覆盖法律安全、平台和品类硬规则；任务确认时冻结规则版本。

### 3.4 用户确认后发布

#### 官方能力观察

淘宝官方商品 API 目录明确存在商品新增、更新、图片和 schema 发布/更新能力；京东官方资料明确查询与修改操作区分；Shopify 官方资料显示管理员权限控制 API 可读写范围，Sidekick 在明确操作下帮助填写和保存商品。

共同点是：平台写入不是普通文本生成，而是带授权、权限、字段约束和远端状态的业务写操作。

#### 对现有 PRD 的最佳落地

发布流程固定为：

```text
生成内容
  → 本地审核
  → 平台预检
  → 展示字段 diff / 不修改字段 / 远端快照时间
  → 用户明确确认
  → 幂等提交
  → 返回受理状态
  → 查询或消息回执
  → 收敛为 published / rejected / unknown
```

必须做到：

- 未经用户确认不写平台。
- 内容批准与发布确认分开。
- 每次确认生成唯一 `PublishJob` 和幂等键。
- 同店同商品不能并发重复发布。
- 远端商品在确认后发生变化时，确认失效并重新生成 diff。
- `accepted`、`审核中`、`published` 不混用；没有平台回执不得显示“已发布”。
- 撤权、401/403、限流、超时和 `unknown` 都必须有可见恢复路径。

## 4. 竞品差距矩阵（仅限 PRD 四类能力）

| 能力 | 美图设计室 | Shopify Sidekick | 官方平台开放能力 | 当前项目应该达到的标准 |
|---|---|---|---|---|
| 授权同步 | 非核心能力 | 单一 Shopify 生态内完成 | 各平台有各自授权、scope、接口和测试流程 | 四 profile 独立 OAuth、读写能力、快照、撤权和回执 |
| 商品详情/主图 | 商品图和参考图强 | 对话生成文案/图片、保存前不写店铺 | 平台商品字段、SKU、图片和 schema 分散 | 事实驱动详情文案；主图引用/预览/保护；不伪造商品事实 |
| 规则/审核 | 提供图像质量操作指引 | 提醒 AI 输出需复核、受权限控制 | 类目 schema、资质、平台规范和远端审核 | 规则版本化、平台预检、P0 阻断、证据和人工最终确认 |
| 确认后发布 | 不是核心强项 | 管理员内自然语言执行并由用户保存 | 提供真实创建/更新接口和远端状态 | diff、二次确认、幂等、回执、对账，失败不误报 |

## 5. 不漂移的最佳解决方案

### 5.1 产品方案

把主流程收敛为一个“单商品、单平台、可追溯商品任务”：

- 一个任务只绑定一个品牌、店铺、商品、目标平台和平台快照。
- 同步数据、用户上传资料、素材权益、规则版本和生成内容全部进入任务快照。
- Codex App 以“已完成 / 待确认 / 被阻断 / 下一步”展示，不把 MCP 字段堆给商家。
- 只有审核通过且用户明确确认，才进入发布预览；只有再次确认才允许写平台。

### 5.2 技术方案

保留现有模块化单体和 `PlatformConnector`，不因为竞品调研拆成新系统：

1. `AuthAdapter`：授权、刷新/重授权、撤权和 scope。
2. `CatalogAdapter`：商品/SKU/价格/库存/图片读取、分页和增量同步。
3. `SchemaAdapter`：平台/天猫/品类字段与资质 schema。
4. `PublishAdapter`：预检、字段 diff、幂等写入、查询、回执和对账。
5. `RuleCenter`：规则来源、版本、有效期、命中证据和阻断动作。
6. `TaskSnapshot`：冻结商品事实、素材版本、规则版本和平台远端快照。

### 5.3 验收顺序

| 阶段 | 只验收 PRD 内内容 | 通过证据 |
|---|---|---|
| A | 四平台应用身份、OAuth、撤权和最小 scope | 每个平台真实授权/撤权记录；无 token 泄漏 |
| B | 商品首次读取、SKU/价格/库存/图片和增量同步 | 四 profile 各一组真实测试店铺记录 |
| C | 详情文案、素材引用、主图预览/保护和审核 | 10 个 P0 黄金任务；事实来源覆盖 100% |
| D | 类目/平台预检和规则命中 | 每个平台至少一组必填、资质、禁用词和图片规则样例 |
| E | 创建/更新商品与回执 | 每个平台至少一条真实 canary；published/rejected/unknown 可对账 |
| F | 失败恢复和版本 | 401/403、429、超时、远端变更、重复提交各有测试证据 |

没有真实平台测试账号或官方沙箱时，对应 profile 只能标记为 `fixture_verified` 或 `contract_verified`，不能标记为 `production_ready`。

## 6. 当前项目的明确判断

结合现有追踪审计，当前代码已经具备较完整的本地业务骨架，但以下内容仍是外部门禁，不能被竞品调研掩盖：

- 京东、淘宝、天猫、拼多多真实 OAuth、读取、创建/更新、查询、撤权和 published 回执。
- 每个平台真实测试账号/测试店铺或官方沙箱的证据。
- 生产图片/LLM/OCR/对象存储等供应商配置及真实产物质量。
- 真实平台规则、类目 schema、资质字段的版本化样例。
- Codex App 对四类 P0 结果的黑盒回归。

因此本轮的产品结论是：

> 先补齐“四个平台真实能力证据 + 任务快照 + 规则命中 + 发布回执对账”，再优化 UI 和生成质量；不通过增加 PRD 外的功能来掩盖平台授权和发布链路未验收。

## 8. 证据边界

官方产品页和开发者文档只能证明“官方公开声明或公开接口能力”，不能证明：

- 本项目已经获得对应应用资质和生产写权限。
- 某个平台的测试账号当前一定可申请或一定可使用。
- 平台最终审核一定通过。
- AI 生成结果一定保留商品细节或符合商家版权要求。

这些事项必须通过真实账号、测试店铺、canary、回执和人工验收逐项闭环。
