# 商品图片工作流参考

本参考提炼自公开仓库 [ecommerce-image-skills](https://github.com/xianyu110/ecommerce-image-skills) 与 [ec-visual-skill](https://github.com/oldred-byte/ec-visual-skill) 的商品身份锁定、套图规划和审核思路。这里只复用概念，不复制其代码、脚本或平台规则；不新增依赖，也不构成独立业务入口。

## 商品身份锁定

生成前从当前工作区已确认资料和用户提供的图片中记录商品身份：外形与比例、颜色、材质外观、包装/标签文字、Logo、按键/接口、配件及 SKU 差异。每张图都沿用同一份身份锁定；只允许改变本次方案明确指定的场景、光线或构图。图片无法证明的内部结构、参数和性能留为未知，不用生成结果反过来证明商品事实。不同 SKU 的外观、规格和素材分开处理。

## 套图顺序与渠道检查

先按买家决策顺序规划，再确认是否适用，不为凑数量硬生成：

1. 首图：让买家看清商品和一个核心用途；遵从当前渠道首图规则。
2. 卖点证明图：只表达已确认且有证据支持的利益点。
3. 细节/参数图：放大可核验的结构、规格和适用 SKU。
4. 使用场景图：展示符合已确认用途的真实任务，不把商品贴进无关场景。
5. 顾虑/体验图：回答连接、佩戴、兼容、续航等具体问题；无证据就省略或标待确认。
6. 收口图：汇总已证明的能力和适用范围；评价、售后、FAQ、价格和购买入口仅在来源真实且当前渠道允许时呈现。

以上是规划顺序，不强制张数或平台模板。只记录当前会话中实际可用的 MCP 工具或服务端返回的渠道规则、来源/版本和读取时间；生成前核对返回内容是否覆盖当前任务的渠道、版位、商品类别、背景、主体占比、画幅/像素、文字与安全区、标签/披露要求及可用 SKU。若未返回具体版位规格或所需检查项目，标为“待核验”并按主技能阻断；不得凭记忆补齐平台规则或把技术预检说成平台审核通过。要求卖家后台确认时，保留待确认状态。

## 套图候选清单与续作

套图方案确认后，为每张候选维护一条清单记录；清单只是对话中的规划与跟进记录，不是服务端状态、审阅证明或可发布 manifest：

| 字段 | 记录内容 |
|---|---|
| 图片槽位 | 稳定的序号/名称、唯一买家问题和画面职责 |
| 商品依据 | 当前工作区商品/SKU 标识；可见事实及对应的已确认来源 |
| 素材依据 | 真实 `asset.upload` 返回的素材 ID、素材角色（商品本体/品牌/场景/角度）及服务端扫描/权益状态 |
| 渠道规则 | 当前 MCP/服务端返回的规则来源或版本、读取时间；缺失或过期就阻断生成 |
| 已确认方案 | 槽位方向、用户确认的文案/卖点、服务端允许的模式和尺寸 |
| 任务证据 | MCP 返回的真实任务 ID、当前状态、候选附件/实际返回的像素尺寸，以及商户创意点扣费或套餐结算状态；缺少实际返回值时记为未知，不推断 |
| 人工复核 | 商品身份、事实声明、规则检查和可读性分别记录通过/未通过/待复核及原因 |

每个槽位分别走当前 Store Nova MCP 的确认、提交和查询门禁；清单本身不能触发批量调用，也不代替方案确认、权限检查、扫描、权益、relay 成本和审计。出现部分失败时，已完成槽位保留其原任务与复核证据；queued 槽位只查询同一任务，禁止重新提交；仅对尚未提交的槽位继续。若要改变已确认槽位的事实、素材、文字、方向或尺寸，先更新方案并再次取得对应确认，再按服务端契约发起新的任务。不能用清单推断任务成功、扫描通过或审核通过。

## 真实性与交付检查

- 对每张候选图按当前任务的服务端渠道规格核对实际尺寸、方向和画幅；检查主体是否被裁切、是否留有方案要求的安全区/文字留白；逐字比对已确认文案，检查可读性、拼写、遮挡、重影、边缘破损及明显像素伪影；按槽位逐一对照商品身份锁定、SKU、输入素材和已确认事实，标出漂移或无证据的内容。
- 以上是人工复核清单，不是机器像素检测。只有当前 Store Nova MCP/服务端对该候选实际返回尺寸、像素 QA 项目及结果等机器证据时，才可将对应项目称为“机器检查通过”；没有此类返回证据时标为“未提供机器检查证据/待核验”。不得把人工观察、对话清单、模型自述或普通生成成功响应冒充工具验证，也不得据此声称整张图片已通过机器 QA。
- 逐张对照商品身份锁定和源素材，检查形状、颜色、标签、Logo、结构、配件及 SKU 是否漂移。
- 每个可见数字、比较、认证、评价、效果、价格、促销、兼容或性能声明都要能追溯到已确认事实；没有证据则删除或标待确认。
- 检查画面是否准确传达该张唯一职责、文字是否可读且未产生额外承诺、不同图片是否有清楚分工。
- 记录渠道规则来源/版本和未通过项。真实性或规则检查失败的图片不能标为通过。
- 图片始终是未批准候选；最终状态、附件、商户创意点结算和审计证据以各自权威来源为准。缺少实际证据时标为未知或待核验。

## Store Nova 执行边界

本参考只指导方案和人工复核。实际上传、生成、查询、编辑和交付只能使用当前 `tools/list` 中可用的 Merchant Marketing MCP 工具及现有服务端中转。禁止调用宿主生图工具、第三方 provider、外部网关、第三方 API/CLI 或本地生成脚本；禁止请求或保存第三方模型凭据。模型鉴权、素材权限/扫描、创意点、服务端用量/成本预检与结算、任务查询、对象归档和审核门禁都由现有 Store Nova 链路执行；服务端成本门禁或结算失败、状态未知/未结算，或必要证据缺项时停在阻断/待处理状态。production/staging/preview 中非排队的模型成功响应还必须含当前 bridge 契约要求的真实 `providerExecuted`、`provider_request_id`、非空 `usage` 和数值 `cost_cny`；缺项时 bridge 失败关闭。排队响应只查询同一任务。内部 relay 证据，不在商家对话展示，也不要求商家提供金额；商户不需要看到或提供精确金额，只有授权 MCP/账务工具实际返回并允许展示时才说明具体 provider 成本；不得估算。
