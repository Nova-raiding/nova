# 平台套餐与权益包管理需求方案

日期：2026-10-05。状态：gstack 多角色、多轮需求评审完成；用户已授权并行实施及 101 部署验收，实施中，尚未通过生产验收。

本方案面向平台运营人员，补齐套餐上下架、价格、功能权限、周期以及权益包的增删改查。推荐扩展现有平台财务中心和 V2 商业目录，使目录配置能够可靠驱动购买、支付、权益授予和 ChatGPT 插件准入。历史价格只作为已有配置记录，不在本次调研中重新批准售价。

## 1 问题与范围

平台运营需要配置销售商品和权益，但现有套餐编辑器只提供名称、类型、价格和自由填写的权益项；销售状态、权益包复用、周期规则和功能权限没有形成完整管理闭环。运营填写成功后，仍可能出现发布失败、停售不阻止购买、权益字段不被运行时消费等情况。

需求来源为本次用户请求；技术问题来自当前主工作目录的代码、测试和本地 PostgreSQL 查询。没有访谈或运营统计数据，因此不推算受影响人数、收入或效率提升。

交付范围为桌面平台运营后台、API/MCP 契约、商业目录、购买与权益运行时、数据库权限和必要 worker。遵循 AGENTS.md：ChatGPT 使用本地直装与 stdio 插件链路；模型继续使用已配置中转，并保留真实鉴权、用量、成本和错误证据；缺配置保持阻断。

### 2.1 必须优先处理的问题

1. **PostgreSQL 发布状态冲突。** `PostgresCommercialCatalogRepository.mutate` 在 publish 时生成 lifecycle=draft、executable=true；migration 146 及本地运行数据库都要求 executable=true 时 lifecycle=approved 且 effective_at 非空。当前代码路径会违反约束。内存实现生成 approved，因此内存生命周期测试掩盖了差异。
2. **停售仍可解析到旧版本。** retire 仅追加 retired 版本，购买解析仍扫描历史 approved/executable 版本。内存复现实测：最新版本为 retired v4，解析结果仍为 approved v3。现有仓储测试甚至断言该结果。真实购买链路尚未执行，不能宣称已复现生产购买。
3. **多个可执行历史版本会导致解析歧义。** 当前解析要求候选恰好一条，缺少独立的当前销售版本。发布新版本不能依赖覆盖历史事实，也不能只取最高 approved 版本，否则会绕过停售。
4. **权益和周期缺少完整语义。** 编辑器把数值写为 quantity，normalizedValue、policyRef 为空；存储单位、按月点数、赠送计划等需要专用校验。月套餐运行时要求 monthly_creative_points，不能用界面上的任意“创意点”字段替代。
5. **版本并发和幂等需补齐。** 当前目录 mutation 输入未包含 expected_revision，仓储没有消费请求幂等键。接口已出现 idempotency_key 字段，不等于数据库落实了幂等。
6. **审批权限需拆分。** 契约中已有 commercial.catalog.approve，但当前 handler 把审批、发布、停售一并检查 commercial.catalog.publish，页面也使用同一权限。
7. **商品身份字段编辑不一致。** 编辑器允许选择类型，PostgreSQL 对已有 SKU 使用 ON CONFLICT DO NOTHING，不能真正更改其 kind。建议 SKU 编码及商品类别建立后固定，改变类别需要新增商品。

## 3 产品结构

在现有平台财务中心设置商品目录，包含套餐、权益包、开通费三个页签；商业订单与异常对账沿用财务中心入口。版本/变更记录进入商品详情，同时保留全局可查询审计视图。保留企业 Workspace 权益页，用于查询实际获得的权益、来源、剩余额度与有效期；详细导航按§15执行。

模型定义：

- **权益项**：系统实际支持的一项业务能力、资源额度或服务承诺。
- **权益包**：一组权益项及数量、有效期和组合规则；可作为套餐组成部分，或以已支持的商品类别单独售卖。
- **套餐**：销售商品及价格、周期、版本、销售状态和绑定的权益包。
- **已授予权益**：某个企业 Workspace 基于具体订单和版本获得的权益事实。

权益包按“可复用的权益组合”设计，同时兼容现有点数充值包。现有 point_pack 不自动获得持续功能权限；若需要单独售卖存储或功能扩展包，必须明确新增商品类别及消费器，不能伪装成点数包发布。

| 功能 | 需求 |
|---|---|
| 列表和查询 | 显示名称、编码、类别、价格、购买周期、当前在售版本、草稿版本、销售状态、权益摘要、更新时间；支持搜索、状态/类别筛选及分页 |
| 新增 | 创建草稿；填写名称、说明、唯一 SKU、类别、价格、周期、可见性与权益包；不直接可售 |
| 查看 | 展示完整价格、周期、功能、额度、绑定权益包版本、阻断原因、历史版本及审计 |
| 编辑 | 基于指定版本生成新草稿；保留原在售版本；价格、周期、权限或权益包变化均展示差异与影响 |
| 审批 | 审批具体版本；通过后可上架，拒绝时保留原因；新草稿不继承源版本审批，在售批准版本及历史合同不受影响 |
| 上架 | 校验批准版本及完整配置，通过事务切换当前可售版本；同一 SKU 只允许一个当前在售版本 |
| 下架 | 禁止创建新订单；保留历史订单、合同、支付和已授予权益；前端、HTTP、MCP 与直接请求结果一致 |
| 重新上架 | 显式选择已批准且有效的版本并重新校验；不因历史 approved 状态自动恢复销售 |
| 删除 | 未发布草稿可逻辑删除；已发布或被引用的套餐只能下架/归档，历史事实不物理删除 |
| 复制 | 复制为新 SKU 草稿，不能复制审批、在售状态或客户订单 |

### 4.1 价格与周期

价格以人民币元输入、整数分持久化；显示币种及对应周期，禁止浮点计费。新订单价格取服务器当前在售版本，不信任客户端金额。按合同及起价商品在具体金额、权益未确定前保持阻断，不能把起价当固定成交价。

用户已确认：套餐价格、一次性开通费、独立售卖权益包价格均可由授权运营修改。本文的开通费 5000 元及套餐 2000/5000/10000 元仅为当前初始价格和计算示例，不是系统固定常量或永久最低金额。开通门槛应判断已完成有效开通订单及资格授予，不判断是否恰好支付 5000 元。

改价通过编辑新版本、审批并发布生效；只有保存草稿不改变在售价格。商家购买、自助升级报价和运营代购统一读取当前批准的价格版本。开通费修改不自动改变每月 500 点、共六个月的赠点配置；变更赠点需另行修改并批准权益版本，已售合同按原快照履约。非独立售卖的内含权益包不产生第二笔收费。

所有已创建且有效的订单及锁定升级报价保留原金额；新购、续购和新升级报价使用生效后的价格。超时订单或报价按原有效期规则关闭并重新生成，运营不能用新价格改写已付订单。通知中的历史发布价保留当时记录，打开商品详情时显示当前价格，并提示价格已更新。

实现时审计并替换普通开通、普通套餐和权益包链路中的金额硬编码，包括订单校验、支付核验、前端文案和升级价差；既有私测转正式抵扣等独立协议仅在相应政策版本批准后调整，不随开通费修改直接重算历史抵扣合同。若改价导致升级目标周期价格不高于当前成交价，不生成负金额收款订单；进入明确的零差额/补偿政策处理，在规则批准前阻断该异常报价。

分别配置购买周期、权益发放周期、点数到期规则。周期模型支持一次性、自然月倍数和固定天数；1/3/6/12 个月及 N 天可以作为管理选项，但只有相应结算、发放、到期与 worker 实现完成后才能上架。已有自然月账期继续使用 UTC 和月末截断算法，不能把一个月等同于 30 天。

例如年套餐可以配置购买周期十二个月、点数每月发放、每批月底到期；也可以配置一次发放。选择必须写入批准版本和订单快照，系统不能自行决定。新增商品默认禁止自动续费扣款，本需求不引入自动扣款能力。

已售订单固定原价格与周期；修改套餐仅影响后续新订单。已支付客户迁移或调整权益必须走单独受控流程。普通下架前已创建且未过期的合法订单继续按原快照支付和履约，过期订单关闭；下架禁止新订单和新升级报价。报价尚未转订单时必须复核在售状态，成功生成的有效待付款订单锁定原价。违规商品的紧急暂停履约属于单独受控风控动作，不等同普通下架。

### 4.2 套餐权限

编辑器区分“功能使用权限”和“额度/服务权益”。功能列表必须来自服务端已注册、确有运行时消费器的业务能力；运营可以选择已实现功能，不能填写一个新字符串就声称系统支持新功能。

功能授权到企业 Workspace，用户仍须具备对象范围及 RBAC 权限。最终放行同时满足身份/租户/对象权限、有效套餐功能授权、商业准入及点数规则、服务与模型 readiness。购买功能包不能获得后台管理权限，也不能绕过无点门禁、扫描、模型配置或发布许可。

HTTP、MCP、本地 stdio Bridge 与 Worker 必须保持同一语义。缺权限应在外部调用前拒绝；异步任务执行前复核权益版本和到期状态；模型实际用量、人民币成本继续记录，不能因套餐包含权益而省略。

## 5 权益包管理功能

| 功能 | 需求 |
|---|---|
| 增查改删 | 创建、详情、查询、编辑新版本、草稿逻辑删除；已被引用版本保留 |
| 基本资料 | 编码、名称、说明、类型、用途、可见性、状态；用途区分套餐内含和独立销售 |
| 权益配置 | 从服务端权益定义选择项目，按类型填写数量、单位、发放规则、到期规则和适用范围 |
| 生命周期 | 草稿、待审批、批准、停用、归档；独立售卖时使用与套餐相同的上/下架校验 |
| 引用关系 | 查看哪些套餐版本和订单引用该包；停用时禁止新绑定，不破坏旧合同 |
| 单独售卖 | 配置价格、有效期、适用套餐和购买数量限制；现有点数包复用 point_pack 链路 |
| 实际授予 | 在 Workspace 权益页显示包版本、来源订单、发放/到期时间、可用/预留/已用及状态 |

权益定义应包括 code、名称、数据类型、规范单位、合法范围、消费器、组合规则。点数按批次入现有创意点账本；存储转换为规范字节数；数量额度明确上限；布尔功能合并为已授权集合；服务时长接入现有履约能力。不能把服务承诺当作 API 权限。

同一权益包不允许重复 code。组合规则按权益定义固定，运营不能任意切换：主套餐绝对额度取唯一有效套餐配置，扩展额度只有注册为增量权益时相加；布尔授权取并集；响应时限等服务条款由合同规则解析。缺少组合规则或消费器时允许保存草稿，但禁止发布。

权益包改为 v2 后，绑定 v1 的套餐与客户权益不自动改变；运营必须明确将套餐升级为新版本。停售权益包不能撤销客户已经购买的有效期内权益；退款回收、补偿及人工赠送继续走已有审批和审计流程。

## 6 生命周期与数据方案

将内容审批与销售状态分开：

```text
内容版本：草稿 → 待审批 → 批准 / 拒绝
销售状态：未上架 → 在售 → 下架 → 重新上架 / 归档
在售版本 v1 + 编辑草稿 v2 可以并存；只有上架 v2 才切换销售版本
```

复用 commercial_catalog_skus、commercial_catalog_sku_versions、commercial_catalog_sku_benefits 和已有订单/权益快照。新增服务端权益定义、权益包及不可变版本、套餐版本与包版本引用、销售状态事件及当前销售投影。具体表名和迁移编号在实施时冻结，不改写历史 migration。

销售投影包含当前版本、状态和 revision，可由事件重建；批准内容保持不可变。上架、下架、版本切换、审计、outbox 和投影更新在一个事务内完成。购买查询只解析“当前在售且已批准的版本”，历史 approved/executable 字段不能自行决定可售。订单快照展开并冻结全部权益，保留包版本引用和完整配置校验和。

所有 mutation 使用 expected_revision、idempotency_key 和请求内容哈希：重放同请求返回原结果，同键不同内容拒绝，冲突返回 409 且前端保留输入。读最新版本、版本编号分配和销售切换需串行化，防止并发覆盖、重复版本或双在售。

全局目录写入仅允许平台运营身份；企业租户无权写全局目录。企业订单、授予记录、账本和服务记录继续验证 tenant FK、ENABLE/FORCE RLS 与最小数据库权限。归档和逻辑删除使用事件或投影，不 UPDATE/DELETE 不可变事实表。

## 7 契约与后台体验

扩展现有 ops.commercial.catalog-v2 接口，或按明确动作拆出草稿、审批、上架、下架、归档、历史查询契约；新增权益定义读取、权益包列表/详情/版本写入/引用查询契约。API 参数使用共享类型与 schema，不能依赖自由 JSON 达成完整业务校验。

商家目录只返回实际在售、可见且当前用户符合资格的商品；Ops 查询支持历史、草稿、停售和归档记录。合法空目录返回成功空列表；仓储不可用返回明确错误，不能把业务空列表统一标记为 503。非公开商品必须权限过滤，不能因编码名称含 private 就假设已隐藏。

权限复用 commercial.catalog.read/draft/approve/publish；权益包按 read/draft/approve/publish/archive 拆分。审批、发布、停售根据动作独立校验；有审批权无编辑权的角色能够完成其获准操作。是否要求双人审批沿用项目的对应风控规则，不因为新增按钮而取消。

桌面编辑采用 Drawer 或分步表单：基本资料 → 价格与周期 → 功能与权益包 → 变更预览。价格、周期、功能授权和权益额度都必须可直接读懂；发布预览显示新旧差异、影响范围及阻断原因。下架与归档提供明确影响提示及确认。

需要独立 loading、empty、error、forbidden、conflict 状态；失败不能清空输入或冒充成功。列表同时展示当前在售版本和待发布草稿，避免最高草稿版本遮蔽正在销售的版本。支持刷新、深链接、键盘操作及焦点恢复，以 1440×900 桌面验收。

## 12 商家购买与升级补充需求

本节依据用户在本次会话的补充要求，扩展商家后台通知、购买、已购套餐和补差价升级闭环；作为目标需求，不表示当前实现已经具备。

### 12.1 商品档位与开通门槛

目标档位为基础版、成长版、尊享版，初始价格分别为 2000 元、5000 元、10000 元，运营可修改。结合现有月套餐实现，暂按元/月建模；其他周期使用已批准的对应价格。尊享版应为明确成交价的标准商品，当前 custom 的“10000 元起、定制报价、权益待确定”不能直接当作尊享版完成；明确成交价不代表价格不可修改。

用户已确认：开通费不包含首期套餐费用，初始为 5000 元且运营可修改。开通费作为企业 Workspace 一次性正式接入门槛，与成长版初始 5000 元月费是两笔不同业务。正式开通后可以按所购档位使用权益，不把开通费解释为永久授予所有档位、所有额度。按当前初始价格，基础版首购合计 7000 元、成长版 10000 元、尊享版 15000 元；改价后首购合计由开通费及所选套餐生效版本动态计算。后续续购只收对应套餐费用，再次升级不重复收开通费。首购采用同一 checkout 的开通费与首期套餐两条明细，可一笔或多笔转账；按明细分配收款，保留两笔独立订单及权益来源。开通费授予正式接入资格与约定赠点，不代替套餐功能或模型调用费用。

开通费包含连续六个月的创意点赠送，每月 500 点，共 3000 点，不是每月 600 点。该数量同时见于历史 PRD、当前 ONBOARDING_OFFER 和支付授予计划校验。六笔赠点独立记录来源、发放和到期时间，不一次性发放全部 3000 点，也不作为首期月费抵扣。

当前代码规则为开通支付核验时发首笔 500 点，其后按月周年发放另外五笔，每笔于下个月周年到期；月末使用现有截断算法。赠点与月套餐内含点数分别入账，升级不重启赠送计划、不重复授予开通赠点。商家购买详情、已购页及点数账本须明确区分开通赠点与套餐点数；每笔到期及发放规则在生产目录和 worker 验收时核实。

门槛校验必须基于服务端已核验的开通订单/资格事实，按 Workspace 幂等，不凭累计充值、钱包余额或购买成长版判断开通完成。正式月套餐及独立权益包单独购买需要检查开通资格；未开通者允许建立包含开通费的首购组合及其依赖订单，但首期套餐/包授予必须依赖开通款足额核验。先付款开通后买套餐同样可用；开通资格本身不授予持续套餐能力。私测、补缴开通费、查询订单等恢复入口使用明确例外，不产生无法开通的死锁。再次升级不重复收取开通费。

### 12.2 上架通知与购买入口

套餐或可独立购买的权益包成功上架后，由同事务 outbox 产生发布事件，再可靠投递商家站内通知。草稿、仅审批通过、发布失败不产生上架通知。通知与现有待处理风险提醒分开呈现，包含商品名称、价格、周期、权益摘要、上线时间、查看/购买链接，并提供未读/已读状态。

按目标企业及其授权用户投递；非公开商品仅通知有资格的对象。只用于内部组合、不可独立购买的权益包不伪造购买入口。发布事件按一次销售发布事件 id 和目标收件人去重；同版本重新上架生成新的发布事件，重试同事件不重复通知，投递和读取时复核当前企业成员及商品可见性，worker 可重试并查询投递状态；通知暂时延迟不阻止读取真实在售目录。下架后旧通知保留，但详情与购买按钮必须显示当前已下架。

商家购买中心统一展示当前在售套餐和独立售卖权益包，读取服务端真实销售状态与批准版本；支持基础/成长/尊享权益比较，显示开通资格和应付明细。现有点数购买弹窗扩展为明确的套餐/权益包入口，不能依赖“咨询客服”完成正常升级。

### 12.3 当前已购套餐

商家后台展示当前生效套餐、订单版本、起止时间、剩余有效期、功能权限、额度及使用情况，同时展示已购扩展包、各自来源和到期时间。订阅历史、待支付订单、已支付待授予记录分别呈现；后者不能显示为已生效。

开通状态独立展示：未开通、支付处理中、已开通或异常待核验。套餐详情提供续购和升级入口，已购记录不能通过取当前目录最新版本重建，否则商品改版会改变历史合同。

### 12.4 自助补差价升级

支持基础→成长、成长→尊享、基础→尊享。先由服务端生成升级报价，绑定当前有效订单和权益版本、目标在售版本、固定 plan_family/tier_rank、计算时点、有效期、差额金额及升级后的权益差额；客户端不能自行指定应付金额。没有当前及已付未来套餐时走新购，同级走续购，降级不混入升级流程；已有未来合同但当前无生效套餐时展示待生效及衔接原因，禁止自动插期覆盖，按下文受控衔接处理。基础/成长/尊享分别使用固定 tier_rank=1/2/3，不随售价变化；身份建立后固定，custom/私测未定义 rank 时不自动参加升级。当前升级只改当前唯一账期，已付未来续期保持原版本、金额、起止时间；界面显示未来待生效套餐。更改未来合同须单独受控流程，不在本次自助升级内。

用户已确认：升级按剩余有效期折算差价，保留原到期日，不重新开始一个完整购买周期，也不重复收取开通费。

同周期升级报价公式为：应补差价 =（目标套餐该周期价格 − 当前套餐该周期成交价格）× 剩余有效时长 ÷ 当前账期总时长。金额使用整数分和有理数计算，最终四舍五入到分；时长按服务端 UTC 起止时间计算，不固定假设每月 30 天。计算时点绑定报价；报价接受截止不得晚于原账期到期，超期不得再生成支付请求。支付成功以可信 provider 成功时间或核实银行到账时间为准，截止前成功到账使用已锁定金额，不因回调/人工核验迟到重算。截止后到账进入异常对账，不静默吞款。核验时原账期已结束，记录已收款待处置，禁止授予过期套餐；经客户确认走已有退款/补偿或转新购流程，原到期日不自动延长。在线支付发起/处理中不等于成功到账。

完整同周期价差分别为基础→成长 3000 元、成长→尊享 5000 元、基础→尊享 8000 元。例如恰好剩余半个账期时，应补分别为 1500、2500、4000 元。示例以当前成交价等于目录价、两个套餐周期相同为前提；跨周期升级在统一换算规则批准前阻断，不能直接相减不同周期价格。

首次升级使用原有效订单成交快照；连续升级时使用上一笔成功升级固定的当前档位周期价格及原账期起止时间，不能拿上一笔差价付款金额当作当前套餐全周期价格。报价、订单和权益切换须保存这些基准及计算结果，确保可重放和审计。

支付核验后原子记录升级事实、切换有效套餐并按版本冻结的 upgrade_policy 补授增量权益；不能再全额发放一份目标套餐点数，也不能把升级当下个账期续购。已有消耗、点数预留和独立扩展包保留来源及到期规则；布尔功能立即切至目标授权集合；品牌/店铺/存储绝对上限切至目标，已用与预留不清零。点数和可消耗服务额度只补额度差的剩余期份额，整点/最小服务单位向下取整，到期沿用原账期。每次计算保存精确有理数和累计余数，连续升级按事件增量累计后扣已授予整数，禁止每次独立取整造成路径不同；生产发布必须验证各档权益单调兼容，否则阻断该升级组合。独立包及开通赠点不参与差额。upgrade_policy 必须包含算法版本、原/目标额度、规范单位、取整/余数、有效期、消耗/预留策略；未批准则不可报价。支付失败保持原套餐，重复回调不得重复升级，两笔并发升级必须通过版本锁与对账处理；已收款但源权益版本已变化的旧报价进入已收款待处置，不以新源版本重新计算或再扣钱，不授予第二份目标权益，经客户确认按退款/补偿或新的独立订单处理。

验收增加：上架→通知→购买列表一致；已购真实权益展示；开通费仅收一次；三个升级方向按剩余有效期报价、付款与权益切换；半周期示例分别为 1500/2500/4000 元；连续升级不重复抵扣、不误用前次差价；月底/闰年、过期报价、目标下架、重复支付回调和并发升级；升级后保留原到期日；真实桌面后台与本地 stdio 插件对同一 Workspace 返回一致结果。

## 13 运营代购与人工转账开通

用户已要求平台运营能够为指定用户开通账户、代购套餐和权益包；用户转账并核验实际到账后开通。该能力与商家自助购买使用同一商品、价格、周期、升级报价、订单快照和权益授予服务，不能另建手工改套餐字段的旁路。

### 13.1 指定客户与创建订单

在平台运营后台的客户详情和商业订单页提供“开通账户”“代购套餐”“代购权益包”“代办升级”入口。通过用户、企业名称或标识查询，选择用户实际所属 Workspace，并在提交前显示企业、目标用户、开通状态、当前套餐、到期日及本次商品；一个用户关联多个 Workspace 时必须明确选择，权益授予目标始终是企业 Workspace。

新客户可以先创建账号、企业工作区并绑定用户，再创建待付款商业订单；账号可登录查询与处理支付，但业务开通资格和付费权益只能在核验到账后生效。复用已有身份与邀请机制，不由运营代设或明文发送用户密码。现有客户不得重复创建账户或重复收取开通费。

运营可以选择一次性开通、首购/续购套餐、独立售卖权益包，或已有套餐的升级。首次正式购买应按生效价格版本分项显示开通费和不包含在其中的首期套餐费；升级沿用剩余有效期报价。首次组合可在未开通时建单，普通单独购买仍校验资格；每条明细显示依赖、应付/已分配/待分配及支付/授予状态。支持关联多笔订单与一个转账核验批次，界面按付款明细显示各项金额和合计；批次关联不替代每笔订单的独立账务和权益来源。

### 13.2 到账核验与权益生效

人工转账待付款订单提供权限受控付款指引：已核实收款户名、开户行/账户、应付人民币金额、匹配订单的附言及成功到账截止，可复制并从原订单恢复；缺少有效收款配置时禁用转账入口。客户提交转账说明或截图只称“待到账核验”，不视为收款事实。

流程为：选择客户与商品 → 创建待付款订单 → 用户转账 → 运营核验收款流水 → 确认到账并开通 → 展示授予结果与商家通知。订单创建或上传转账截图不能直接视为已收款；核验须记录真实收款账户、付款方、实际到账金额与币种、到账时间、银行/支付流水号及证据引用，由有支付核验权限的运营执行。

服务端从订单快照取得应付金额和权益，并校验到账证据与订单分配。收款不足、币种不符、订单失效或无法确认到账时保持待核验，显示差额和处理原因，不静默修改售价或免费开通。可分笔收款，但同一收款流水的已分配金额加本次分配不得超过实际收款；一个流水覆盖开通与套餐等多项时要显式分配，不能靠流水号唯一性禁止合法拆分，也不能反复使用一笔款开通多次。

核验后，支付状态、开通资格、套餐账期/升级事实、点数及资源权益、开通赠点计划、审计和 outbox 必须在规定事务边界内一致提交。无当前有效套餐且无已付未来合同的新购默认从核验完成时生效；同级续购采用§16浮动顺延，付款前展示预计起止及顺延说明，核验提交后固定合同起止，不覆盖当前/未来合同；待支付续购保留原价格/档位快照、有效期与顺延策略；原始到账时间单独留存，不允许前端默认覆盖真实收款时间。升级按§12.4的可信成功到账时点及核验时原账期/源版本判断已锁定报价，不能用核验当前时点重新改价或自动延长原到期日。一个 Workspace 的首购组合收款分配、开通事实与满足依赖的足额明细在同事务提交；部分到账只完成已足额且依赖满足的明细，套餐未足额时不可授予。若只套餐足额而开通未足额，显示已分配待开通依赖，不可激活。各企业批次独立提交，不以跨企业大事务伪装全成功；异常项保持待核验/已收款待授予或待处置，提供对账重试入口，不把部分完成显示为全部开通。

普通账户开通费核验后创建六个月、每月 500 点的唯一赠送计划；套餐和权益包按各自规则授予。操作结果按实际状态分别显示“到账已核验”“账户已开通”“套餐立即生效 / 未来待生效 / 待依赖 / 待处置”“权益包已到账”，返回订单、授予和审计标识。异步通知发送失败可重试，不能因此重复收款核验或发放权益。

商家后台显示“运营代购 / 人工转账”订单来源、分项金额、当前套餐及已购权益包，并收到开通/购买/升级结果通知。只有本人及所在企业有权限的用户可查看；平台运营权限不直接向商家开放。

### 13.3 权限与验收

账号创建、代建订单、核验收款、人工例外授予分别消费对应权限；沿用现有确认与审计规则。权限不足时在服务端拒绝，禁止运营通过冒用商家会话跨租户下单。每次操作记录运营操作者、目标企业、目标用户、商品版本、原因、收款证据与结果；请求和支付流水分配均实现幂等及并发保护。

新增验收覆盖：新客户开户后首次转账开通、已有客户代购/续购、权益包代购、按剩余有效期代办升级、开通费与首期费用分项、重复开通/重复核验/重复流水分配、分笔与合并转账、到账不足、跨租户与越权拒绝、事务失败恢复，以及商家通知、已购权益和本地插件准入的一致性。另需分别改动套餐、开通费和权益包价格，验证商家自购、运营代购及升级新报价一致使用新价格，而有效旧订单、已购权益、开通赠点和锁定报价保持原快照。使用真实 PostgreSQL 和授权桌面运营会话验证；生产开通声明需真实转账回执证据。

当前实现已有 `ops.commercial.order.payment.verify` 和 `verifyCommercialOrderTransfer`，可核验普通开通/月套餐/点数包订单，并有“私测转正式与人工转账”面板；这是复用基础，尚不能替代完整的指定客户开户、代购、收款分配和升级闭环验收。证据：`packages/contracts/src/mcp.ts:885`、`apps/ops-console/src/api/commercialOperationsClient.ts:609`、`apps/ops-console/src/components/commercial/CommercialOperationsWorkspace.tsx:509`。本次只更新需求，未为任何真实用户创建订单或开通。

## 14 对账、可观测与回滚

所有链路串联 request/checkout/order/quote/receipt/allocation/grant/outbox 标识，Ops 可查已到账待授予/待处置、分配余额、赠点漏发及通知死信，显示原因、最老时间及获授权恢复入口。提交响应丢失先按幂等键查询真实结果，再重试原业务服务，禁止手改余额或复制订单。证据只留权限受控引用，日志不输出完整凭证、密码或敏感账户资料。

迁移采用 expand→兼容代码关闭新写→目录人工核对→worker及真实闭环验收→开放新写。回滚首先关新购/新升级/目录新发布，不停止合法旧单核验、已付授予、查询、赠点和到期worker；保留迁移与不可变事实，用兼容代码回退，不能删除业务/容器数据。旧新实例混跑必须共同遵守销售投影，否则禁止开放新写。

人工收款事实与订单分配分别建账：每笔真实流水有持有人/目标企业（未匹配时标未知）、收款核验人、对账负责人、下一处理期限和未分配余额。多付款、过期订单到账或无法匹配款须进入异常队列，逾期提醒负责人；经付款方确认及权限审批后关联新有效订单或退回原付款方，记录返款流水/证据和金额守恒。未分配收款退回使用独立 receipt-return 事实与审批，不伪造 paid 订单调用现有仅支持已付订单的退款入口；退款处理完成才关闭异常，无法核实退回保持待处置。禁止自动吞并、钱包余额或静默抵扣。验收覆盖多付、未匹配、过期到账、重复返款及并发分配/退回。

## 16 工程事务、权限与容量边界

新购、首购明细、升级报价转订单在同一数据库事务内通过受控销售解析函数重新读取在售状态、批准版本、资格/可见性并锁销售投影，保持至订单快照提交；上/下架及切版取得冲突写锁。事务外查目录或缓存快照不授权建单。函数固定search_path、校验企业上下文、拒绝PUBLIC EXECUTE、仅授权最小EXECUTE和返回字段；merchant_app不因并发锁而获得全局目录表访问权限。真实migration后再执行role bootstrap，验证最小权限、RLS及停售/建单两个先提交方向；有效旧单核验按历史快照，不重新依赖当前在售状态。

所有共享写路径统一锁序：销售投影（如需，SKU排序）→真实收款可用余额（如需，流水id排序）→Workspace事务锁→checkout/订单（id排序）→当前账期/权益版本→点数状态/账本。纯目录只锁投影；普通建单跳过收款锁；旧单支付授予跳过销售锁；返款/退款/赠点/到期worker只能按兼容顺序获取所需子集。现有order-first路径必须按调用图一起调整，不能仅给新方法加锁。不存在的账期行以Workspace事务锁序列化，不靠空结果row lock；跨企业批次分企业提交，不在持锁时切换租户上下文。

收款外部真实身份按来源、收款账户和外部流水标识唯一，不得更换内部id重录同款；冲突需核实来源证据，不可自动合并两笔不同款。可用余额=实收−有效分配−已退回−待退回冻结金额，金额均整数分。分配与receipt-return共用余额锁，返款审批先冻结余额，失败按受控事件解冻，外部结果未知保持冻结并查询原返款意图，不能因超时再次发送。外部支付/返款和通知调用在数据库事务外执行；幂等重试先查提交事实，再有限重试同一意图，不新建收款/退款。租户只见自己事实，跨租户余额守恒由最小受控服务核验，不开放其他企业明细。

发布事务只插入一次outbox事件，不遍历全体收件人。租约worker按持久游标分批fan-out，首期每批上限200，事件id/收件人唯一键、崩溃重跑不漏发或重发，逐批复核成员及可见性。列表默认50、服务端最大100，历史、异常及通知用稳定游标；限制可作为运行配置调整，但不能绕开服务端上限及容量验收。权益包引用无环，数量/展开体积必须有schema限制，超过限制明确拒绝。

上线记录目录/建单/分配事务耗时、锁等待、通知backlog及最老消息、赠点延迟、连接池和容器容量；用发布门禁批准的真实负载验证，不编造客户数或线上p95。目录缓存带sale revision仅服务展示；写入复核、资格及余额均以事务事实为准。工程测试分支图和20组行为覆盖计划见 `docs/qa/package-review-2026-10-05/eng-test-plan.md`，其中14组新行为必须随实现新增测试，既有单元/fixture或PG测试源码存在不能证明通过。

订单创建必须锁定付款接受截止expires_at及策略版本，实际成功到账时间而非发起时间决定是否在窗口内。普通新购/开通/包订单截止前到账而核验晚到，仍履行原快照；无当前及已付未来套餐的新购从核验完成起算，续购按锁定顺延策略与现有账期重检。截止后到账或已无法履约的款进入已收款待处置/未分配队列，经付款方确认退款或新订单，不自动按新价改原单。升级另按§12.4保留原到期与期满异常规则。已开通企业不再授予或收费第二次开通；同Workspace仅允许一个有效待付款开通意图，重复建单返回可访问的原意图或明确冲突，旧意图关闭后方可新建；竞态重复开通到账进入资金处置而非重发资格/赠点。验收覆盖普通订单截止前到账晚核验、截止后到账、同时首购及续购账期变化。

### 16.1 截止与续购的确定语义

普通订单的到账截止来自批准的订单有效期策略，创建时冻结expires_at和策略版本；缺少策略禁止建单。支付链接自身到期不改变订单截止，可在订单窗口内重建链接但不延长订单；成功到账须早于截止（半开区间）。分笔款以截止前可信到账的可合法分配金额累计是否足额判断，允许晚核验/晚分配，但不允许伪造/回填到账时间；截止后才足额进入已收款待处置。首购各条明细独立判断并检查开通依赖，关闭订单与核验使用同一锁/事实排序。实际到账总额、已分配及未分配守恒。

本期新续购只采用floating_append策略：按Workspace核验事务提交顺序，起点为max(核验完成时点，当前及已付未来有效合同最晚终点)，终点按订单冻结周期/周年锚点计算。待支付时日期标“预计”，付款前告知可能因其它续期顺延；核验提交后日期固定，幂等重试返回原期间，不再重新顺延。同一Workspace两张续购单按提交顺序连续追加，不覆盖或共享同一窗口。遗留固定窗口合同只按原快照处理，发生窗口冲突进入已收款待处置，本期不新建固定窗口商品。

当前升档不更改升级前已创建且有效的原档位待付款续购；它仍可按原价/档位和floating_append成为未来合同。升级确认同时显示已付未来及有效待付款续购，并明确“本次只升级当前期，未来订单仍按原档位”；需要改变未付款续购时由授权用户先取消原意图再按当时档位建新续购，取消不影响已收款事实。既有已付未来合同仍不可重写。新建意图由服务端按有效当前档位判定新购/续购/升级，同档续购，升档走专用报价；并发状态变化不能将新购自动转升级或全价收费，无法按原意图履约进入待处置。

未来已付合同核验后创建待生效权益及唯一发放计划；套餐点数/可消耗服务默认不早于对应账期开始进入可用余额，未生效量不参与余额、预留或消费。按批准发放时点由worker转可用，崩溃重放沿用原计划、来源和到期，不提前发放、不重启。错过已经结束的发放窗口不补成新的未过期权益，记录漏发/过期事实及售后处置。开通赠点及独立包仍各按自己的批准时点，不因未来续购改变。

正常已付未来合同及计划状态为“未来待生效”，不当作授予故障；只有应生效/应发放却失败才显示“已支付待授予”异常。核验结果和商家通知逐项使用实际状态：立即生效、未来待生效、待依赖或待处置，不能统一称套餐已生效。无当前但有已付未来合同的间隙，新增整期即时套餐可能重叠既有窗口，本期禁止自动插期/覆盖，提供原合同查询和Ops受控衔接入口；不把这个状态误判从未购买，不自动移动未来合同、补猜短期价格或降档。任何订单核验时若新购前提已变化，由版本/账期约束拒绝自动改意图并进入资金处置；当前与未来任一主套餐窗口不得重叠。

### 16.2 来源限定的退款与恢复

新合同/订单接入退款前必须定义并批准source_recovery_policy及对应执行器，在外部返款前完成预检及必要冻结；禁止直接复用按Workspace全局负点数调整回收新订单权益。回收只针对该订单及派生grant/计划/期间，不能扣无关赠点、独立包、其它套餐的余额；历史事实保留，以退款/补偿事件更新投影。

已收款待处置且从未授予的订单退款只返该单实际已分配金额，不调整任何点数；未分配款走receipt-return。未来续期退款取消该来源未生效期间及未发批次，不影响当前或其它未来合同。已授予可消耗量只回收该来源未用且未预留部分；已用/预留、已履约服务需批准补偿政策，缺失时阻断自动退款执行并由受控售后处理，不转扣其它来源。

升级退款须绑定升级事件：仅当该期仍有效、当前权益仍是该升级结果、无后续依赖变更且增量未消费/预留时，按批准政策回收该增量并追加恢复源档位事实，原起止不改；其它情形进入人工审批的补偿/依赖处理，不能盲目恢复旧档位或改未来合同。开通退款须核对赠点计划与所有依赖合同，政策/执行器不完整时禁止撤销资格及外部自动退款；不得只删赠点计划就令有效套餐失去准入。

外部返款结果未知保持冻结并查询原意图；外部成功、本地提交失败进入退款待同步，重试同一事实并阻止二次返款，回滚代码必须继续处理已批准意图。新增验收：普通截止/分笔跨截止/链接重建、两张续购顺序互换、续购与升级交错、未来额度不可预留/消费及生效worker重放、无授予退款/未来续期退款/升级退款/开通依赖、无关来源不扣、外部成功本地失败恢复。具体商品政策缺失显示明确阻断，不允许旧通用负点数旁路执行。

## 17 本地插件契约、支付模式及文档验收

### 17.1 精确注册与安装兼容

所有新商业动作、报价引用、输入/响应版本和恢复查询同步到共享MCP exact registry、HTTP/OpenAPI、Bridge工具schema和类型客户端；商家tools/list不能发现Ops方法。升级建单强制引用有效服务端报价及源权益版本；旧客户端只有purchase_kind=upgrade和SKU时返回明确不支持/更新提示或获授权桌面入口，禁止回退普通月套餐全价。服务端也拒绝绕过该规则的直接HTTP/MCP请求。

实施候选冻结支持版本矩阵：当前服务端/当前已安装插件、当前服务端/支持窗口内旧插件、回滚兼容服务端/新插件。兼容期保留合法旧单查询与履约；未知契约版本禁新写、不猜字段；不支持版本提供原安装手册更新指引与新会话验证，不要求手改缓存。以实际本地安装包验证tools/list/schema、版本/缓存和三组矩阵，不能只验证仓库Bridge文件。

零点及未知点数余额下仍允许获授权的目录、首购、查单和商业恢复，各具体方法/动作精确注册；只豁免这些不产生模型调用的方法的点数预算前置阻断，不豁免身份、Workspace/RBAC/RLS、商品/开通资格、付款事实及支付模式readiness。资格/商品/资金事实未知仍阻断对应写入。禁止commercial.*通配豁免或因客户端next_actions解除服务端权限。

### 17.2 已批准人工转账模式

服务端选择已批准线上模式或manual_transfer并冻结到订单。人工转账依赖该模式已核实的收款配置、真实流水和核验权限，不以未启用微信/支付宝provider的配置缺失拒绝合法代购，不伪造线上checkout链接。没有任何批准模式、收款配置无效或核验策略缺失时阻断相应建单/付款入口并列管理员待补项；不可任意填provider字符串或用sandbox在生产开通。各模式独立输出能力/readiness与原因，并用同一核验/授予事实服务。

### 17.3 可验证的错误与安全恢复

商业错误采用稳定机器code、HTTP/MCP对应语义、安全业务原因、字段错误/阻断项、request_id/trace_id、retryable及获授权next_actions；具体schema在实现冻结。区分配置缺失、动作无权、输入非法、revision冲突、结果未知及已收款待处置；说明是否已产生订单/收款/授予、责任人和恢复入口。Bridge安全白名单保留所需业务恢复字段，不透传secret/堆栈/完整凭证；next_actions与exact registry及服务端权限求交，每次执行再次授权。

缺配置/越权/非法字段三路径必须测试安全输出与恢复：配置列待补项不让重付，无权保留获授权草稿/读入口，字段错误定位并保留输入。新增冲突、源升级版本变化、提交结果未知与503也需契约测试；先查原请求/订单/返款意图确定状态，未知时保持待确认，不将所有503视为可以新建或再付款。支持人员只使用受控请求/订单标识排障，不索取密码/token或未脱敏凭证。

目录查询或首次建单前受阻、尚无订单/任务/工单时，错误页和安装排障文档提供已配置的项目内支持交接入口，允许复制脱敏request_id/trace_id、版本和失败步骤。授权支持人员核实企业后按既有工单机制登记，返回工单标识和该客户可见回复入口；request_id不是查他人记录的权限证明，不向商家开放Ops创建权限。入口未配置时明确列待配置项及安装/运营负责人，不把“查询已有回复”称为已提交求助。验收无业务标识的首次求助、真实登记后回复查询、跨企业拒绝及凭证脱敏。
