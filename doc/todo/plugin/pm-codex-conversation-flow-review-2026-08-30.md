# Codex App 插件交互审查

**身份：** 产品经理 / 用户倡导者  
**日期：** 2026-08-30（Asia/Shanghai）  
**范围：** 商家在桌面 Codex App 中安装、发现、配置店铺、上传素材、生成内容、审核、发布和使用 Automation 的对话流；Merchant Studio 仅作为开发调试和结构化 UI 证据参考。  
**结论：** 当前安全门禁和领域状态较完整，但用户仍很难在一次对话中回答三个基本问题：**我现在处于哪一步、这个数据是否真实、我下一步具体要做什么。** 下列问题按对任务成功率、错误操作风险和信任损耗的综合影响排序。

## 判断基线

- Codex App 的基本心智是“在对话中调用应用，并在需要时使用卡片/交互 UI”；用户不应被迫记忆 MCP 方法名或内部参数。[OpenAI Apps](https://openai.com/index/introducing-apps-in-chatgpt/)
- 外部写操作需要在执行前让用户确认，且宿主/工作区权限仍然有效；插件自己的确认不应被表达成“已经发布”。[OpenAI Apps in ChatGPT](https://help.openai.com/en/articles/11487775-connectors-in)
- 本仓库明确把 Merchant Studio 定义为开发调试控制台，把真实 Codex App 宿主证据作为独立发布门禁；因此本审查不把本地浏览器页面的通过等同于 Codex App 真实宿主通过。

## 10 个最影响可理解性和可操作性的问题

### 1. “我在 Codex App 里用什么”与“我在 Merchant Studio 里看什么”没有形成单一产品入口

**影响：P0｜信任与任务起点**

README/使用说明说商家只需操作 Codex App，Merchant Studio 不是前置条件；但现有 dogfood 主体是 Merchant Studio 页面和浏览器证据。真实 Codex App 目前仅有四个只读入口通过记录，完整宿主门禁仍要求插件发现、启动、充值入口、OAuth 入口、附件和错误恢复六类场景。用户无法判断应该安装插件、打开网页工作台，还是等待管理员配置宿主。

**验收标准：**

- 新用户只从 Codex App 开始，首条响应明确显示“已启用插件 / 未启用插件 / 需要管理员配置”三者之一，并给出唯一下一步；不要求打开 Merchant Studio。
- 帮助或诊断中把 Merchant Studio 标为“开发调试，不是商家入口”，不得出现可让商家误点的“去工作台完成配置”措辞。
- 真实桌面 Codex App 逐项通过 `plugin_discovery`、`merchant_start`、`wallet_recharge_entry`、`platform_oauth_entry`、`asset_attachment`、`error_recovery`；每项包含同一 release 的证据引用，console/network error 均为 0。未通过时在插件入口明确显示阻断原因，而不是显示正常业务首页。

### 2. 首次引导有多个“第一步”，对话无法稳定收敛到一个动作

**影响：P0｜首次任务完成率**

文档要求的顺序是工作区 → 平台授权 → 健康 → 钱包 → 上传素材；Skill 又把默认导航写成“知识库 → 商品 → 图片 → 素材”，页面同时提供“创建营销任务”“同步全部店铺”和四张 New Session 卡片。对第一次使用者来说，这不是选择自由，而是要猜系统真正的先后关系。

**验收标准：**

- `merchant.start` 只返回一个当前步骤、一个主 CTA 和不超过两个辅助选项；其他入口折叠为“稍后处理”。
- 首次状态至少可显示：`1 工作区`、`2 连接店铺`、`3 选择/导入商品`、`4 补充素材`、`5 生成并审核`、`6 发布`，并且当前步骤与服务端状态一致。
- 每个步骤的 CTA 都是用户语言（如“连接淘宝”“上传商品资料”），响应结束再次说明“下一步是……”；用户说“开始使用”时，不能同时发起同步、生成或创建任务。
- 5 名未看文档的商家中至少 4 人能在 60 秒内说出当前步骤和下一步，且不会打开 Merchant Studio。

### 3. 店铺连接、授权可读性、平台能力和店铺选择被混成同一层状态

**影响：P0｜误操作与数据串店风险**

截图中同一连接区同时出现“已连接”“需授权”“撤销”，平台卡片还出现 `CONFIG_MISSING`、`0/9 canary`、`未验证`。同一平台多个店铺的展示也没有把“平台 + 店铺 + 当前可读性 + 写入能力”作为一个可决策单元。用户可能以为“已连接”就能同步或发布，也可能点到错误店铺。

**验收标准：**

- 每个店铺行只显示一组面向用户的状态：`可读取`、`需要重新授权`、`已撤销`、`仅有账号记录`、`平台暂未配置`、`演示连接`；技术原因可展开查看，不能以 `CONFIG_MISSING` 作为主标签。
- 店铺级 CTA 明确为“连接京东 / 重新授权 / 查看历史 / 选择此店铺”等，不使用无上下文的“连接”“撤销”。
- 同平台多店铺必须展示平台、店铺名/别名和可读取状态；未得到用户明确选择前，任何商品、同步、任务和发布调用均不发出。
- 选择后，对话确认卡固定显示“平台 + 店铺 + 商品范围”；服务端请求固定带同一 `platform + accountId`，缺失、冲突或授权不可读时阻断并给出修复 CTA。

### 4. 演示数据、fixture、账号记录和真实数据的视觉与语言边界仍不够强

**影响：P0｜用户信任与业务决策风险**

当前页面的“最近动态”多项带“演示数据”，小红书显示“未验证 Fixture”，同时连接区、能力证据和业务摘要都在同一首屏出现。仓库虽然要求不以 fixture 替代真实证据，但用户看到的整体仍像一个已经接入的工作区，尤其容易把示例商品、示例发布状态或本地扫描当成自己的真实结果。

**验收标准：**

- 所有非真实数据在标题、状态徽标和详情中同时标注来源：`演示 / fixture`、`仅账号记录`、`官方 API`、`本地缓存`；不能只在页面底部或一条动态里标注。
- fixture/演示数据不得进入“我的商品”“我的发布”“已连接店铺”默认列表；若提供示例体验，必须单独命名为“查看示例”，且明确“不属于你的店铺，不会发布”。
- API/宿主返回失败或未配置时，不展示演示数据作为成功结果；只显示失败说明、影响范围和重试/配置动作。
- 用户确认或发布前的摘要必须包含数据来源和最近读取时间；测试人员能用一眼判断“这条数据是否可以用于真实经营决策”。

### 5. 钱包/套餐/模型行动额度的状态互相打架，用户不知道究竟被什么解锁

**影响：P0｜付费理解与任务中断**

页面证据显示“插件钱包与能力解锁｜已解锁｜¥159.63｜剩余 29 次”，但同一模块又写“充值后开放内容、图片、视频生成及发布确认”；文档还规定余额为 0 时可查看和授权、生成与发布需充值。即使这是不同快照，用户无法知道余额、套餐次数、模型 readiness 和平台写入权限分别是什么关系。

**验收标准：**

- 钱包卡拆分显示四个独立事实：`余额`、`套餐剩余次数`、`生成能力`、`平台发布能力`，每项带 `已解锁/需充值/平台未配置/需人工确认` 单一状态。
- 不允许在同一状态下同时出现“已解锁”和“充值后开放”；若能力部分可用，必须逐项说明可用范围。
- “充值并解锁”按钮只在确有可解锁能力时出现；提交订单后显示 `待支付`，支付回调确认后才改为 `已到账`，并提供“刷新到账状态”。
- 生成、图片、视频、OCR 和发布被阻断时，错误卡明确指出阻断者是余额、套餐、模型配置、素材权益、平台能力还是人工确认，并且只提供对应动作。

### 6. 首页把高风险总数和技术证据堆给用户，却没有把问题转成可执行队列

**影响：P1｜恢复效率**

“需处理问题 47，其中 47 项高风险”、六个平台 `0/9 canary`、同步恢复区和能力证据区同时占据首屏；但用户真正需要的是“哪个店铺的哪个商品，现在做什么”。计数没有按影响、店铺和下一动作组织，技术证据也没有和具体阻断关联。

**验收标准：**

- 首屏最多展示 3 个最高优先级问题，每项包含：影响对象、用户能理解的原因、风险后果、主 CTA、次 CTA（查看证据/稍后处理）。
- “47”必须可展开到按平台/店铺/商品分组的可处理列表；没有可执行项时显示“暂无需要你处理的问题”，而不是仅显示计数。
- `CONFIG_MISSING`、`0/9 canary` 等技术证据移入“为什么不能做”详情，并链接到“连接店铺/联系管理员/重新检查”等动作。
- 任何失败、空数据和未配置状态都能被用户明确区分；失败重试不清空此前已成功读取的结果。

### 7. 面向商家的输出仍暴露了过多内部术语和状态机语言

**影响：P1｜可理解性**

Skill 要求最终只展示商品信息、可复制文案、主图预览、店铺分析和下一步，但现有可见证据仍出现 `NEW SESSION`、`CURRENT SCOPE`、`CONFIG_MISSING`、`canary`、`fixture`、`account_id` 语义，以及平台英文机器标识。安全诊断需要这些信息，但日常商家任务不应先读懂系统实现。

**验收标准：**

- 默认商家回复不出现 MCP 方法名、JSON、内部 ID、hash、revision、`account_id`、`canary` 等词；技术信息只能在“查看技术详情”展开区出现。
- 所有状态有统一中文名称和一句解释，例如“需要重新授权｜目前无法读取该店铺商品”。
- 主卡片优先显示商品名、店铺名、平台、任务状态和下一动作；机器值仅作为可复制的诊断信息，且不抢占主视觉。
- 术语抽查中，5 名商家至少 4 人能解释“已生成”“待审核”“已提交”“已发布”“结果未知”的差异。

### 8. Codex App 的附件入口和“上传自己的商品”路径没有被证据完整闭环

**影响：P1｜首次价值实现**

文档要求用户在 Codex 新会话输入框左下角点击“+”上传图片、PDF、Word、Excel、CSV 或文字资料；Skill 也要求收到附件后先展示文件名和数量。但现有主证据是本地 Merchant Studio 的页面流，不能证明真实 Codex App 能看见附件、把附件传到正确工作区，或在解析失败后恢复。

**验收标准：**

- 在真实桌面 Codex App 中，从“上传我的商品”开始，用户能看到附件已收到的文件名、数量、类型、大小和当前工作区；不要求复制 base64 或文件路径。
- 附件逐个显示 `待安全扫描 / 扫描通过 / 解析中 / 解析失败`，并提供“重试解析”或“人工填写事实”；解析失败时保留文件和已提取结果，不伪装成 OCR 成功。
- 用户未上传附件时，响应只给出“点击输入框左下角 + 添加……”这一动作，不自动选演示商品、不自动生成概念图。
- 附件、素材权益、商品事实和店铺绑定在最终确认卡中可追溯；错误恢复场景满足宿主证据门禁的 `asset_attachment` 与 `error_recovery`。

### 9. 异步同步/生成/发布任务在对话中缺少稳定的进度、恢复和“未知”语义

**影响：P1｜可操作性与结果信任**

仓库已有 `catalog.sync.get`、`task.resume`、时间线和 `unknown`/`reconciling` 等状态，但这些能力主要存在于协议和后台语义里。对话用户需要知道任务是否仍在运行、是否可以离开、回来后如何继续，以及“未知”时不能重复发布。

**验收标准：**

- 每个异步任务响应都显示：任务名称、平台/店铺/商品、当前状态、最近更新时间、已完成/总数或“进度未知”、下一次可执行动作。
- 对话结束时生成可复用的“继续处理”入口；新会话说“继续上次任务”可从服务端恢复，不重复创建任务、不默认重试、不丢失店铺范围。
- 状态 `submitted`、`reviewing`、`published`、`rejected`、`unknown`、`reconciling` 使用不同的用户文案；`unknown` 只能给“人工对账/查询状态”，不能显示成功或提供再次发布作为默认 CTA。
- 长任务失败时保留成功项和失败项清单；重试按钮只重试可重试项，并在发起前再次展示范围。

### 10. Automation 的入口、频率和历史能力没有形成可验证的 Codex App 体验

**影响：P1｜可操作性与信任**

文档说明 Automation 由 Codex App 原生调度、历史和通知负责，插件只提供模板；同时又记录 App Server 返回 `null`，From Plugins、创建、Run now、历史和通知尚未完成真实 canary。历史审查曾发现文件名/文案为“每周六平台经营简报”，但 `weekly-six-platform-digest.json` 的 `schedule.days` 是 `MO`（周一）；当前源码与 marketplace 镜像已修正为 `SA`（周六），并由 `tests/plugin-manifest.test.ts` 固定回归，真实宿主证据仍未完成。

**验收标准：**

- 在真实桌面 Codex App 的插件入口能看到两个模板，创建页明确显示频率、时区、下次运行时间、只读范围和不会执行的动作；不可用时显示“当前宿主未提供 Automation”，并提供完整可复制模板。
- “每周六平台经营简报”的机器配置必须使用宿主约定的周六值（若宿主 schema 使用 ISO weekday，则为 `SA`/`6`，以真实 schema 验证为准），UI 文案、JSON、预览和下次运行时间一致；不得出现 `MO`。
- Run now 只调用 `workspace.health` 和 `workspace.metrics`；运行历史显示成功、失败、数据不足和 `comparisonAvailable=false`，不得在没有宿主基线时声称“新增/持续/恢复”。
- 报告首行不泄露店铺名、商品名和内部 ID；详情按平台/店铺隔离，并为每个风险提供“查看 / 连接 / 新建交互会话处理”动作。

## 建议的修复顺序

### 2026-08-31 状态语义增量

Merchant Studio 已将平台账户的 provider 状态转换为面向商家的单一状态文案：可读取、演示连接、仅有账号记录、需要重新授权、已撤销、平台暂未配置和连接状态待确认。演示账户不再提供同步动作，账号记录存在但不可读时明确引导重新授权，避免将“已连接”误读为可读取。状态映射由 `platform-connection-status.ts` 单元测试覆盖；真实 OAuth、权限矩阵和正式 Codex App 宿主验收仍未完成。

### 2026-08-31 首次引导结构化动作增量

插件桥接层现在从服务端 `onboarding_v2.current_step.primary_action` 生成唯一 `conversation_state.primary_action`，并将辅助动作限制为最多两个；商家可见文本仍只保留自然语言问题，不暴露 MCP 方法名。自动安全扫描期间不输出 `asset.scan` 或管理员/运营后台动作，只播报“处理中、无需操作”。源码 bridge、marketplace bridge 及测试镜像保持字节一致，插件/MCP/OpenAPI/对话流回归 75/75 通过；正式 ChatGPT Host 的真实首条消息、附件和错误恢复证据仍未完成。

1. **先统一入口和状态模型：** 解决真实 Codex App vs Merchant Studio、首次步骤、店铺状态、演示/真实边界和钱包能力五项；这些问题会让后续所有 CTA 失去可信度。
2. **再重写对话输出：** 把技术证据降级到可展开诊断，把风险总数变成可执行队列，所有异步任务补齐进度、恢复和未知结果。
3. **最后做宿主闭环：** 用真实桌面 Codex App 验证附件、错误恢复、OAuth 入口、插件发现和 Automation；在真实证据产生前，产品和发布文档必须明确保持阻断，不用本地 fixture 或 Merchant Studio 通过替代。
