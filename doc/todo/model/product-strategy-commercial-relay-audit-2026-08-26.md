## 一句话结论

大麦已经不是“文案 Prompt 插件”，而是一个以 Codex App 为对话入口、覆盖多店铺商品事实、品牌知识、内容生产、视觉候选、审核、版本、发布与运营审计的电商内容操作系统雏形。代码闭环较完整，真正阻碍商业上线的是三件事：真实平台与模型/支付证据不足、商家首次体验仍像工具箱、计费模型同时使用套餐额度与钱包且缺少真实成本账本。

## Strategy Kernel

**诊断：** 电商卖家缺的不是另一个会写文案的大模型，而是一条能读取真实商品和店铺上下文、避免 SKU/价格/权益错误、经人工确认后安全落到多平台的生产链路。通用 AI 便宜甚至免费，单纯“生成更多内容”无法形成长期壁垒。

**指导方针：** 聚焦“事实可信 + 多店铺作用域 + 可审核发布”的商家工作流；Codex App 负责自然语言入口和工具编排，大麦负责数据、规则、模型中转、账务、版本、发布和证据。先把一个平台的真实闭环做到稳定，再复制统一连接器合同到其他平台。

**力量来源：** 商品事实、品牌规则、素材权益、历史反馈、平台回执和成本数据形成链式系统。竞争者可以复制一个生文或生图按钮，但难以复制跨店铺的可信上下文、确定性门禁和可恢复发布证据。

**不做什么：** 不按“模型更强”定价；不让商家管理供应商 Key；不把 fixture 称为生产能力；不做无人确认自动发布；不在真实 canary 前同时承诺六平台完全可写。

## 已解决的卖家痛点

| 卖家痛点 | 大麦当前解法 | 商业价值 |
|---|---|---|
| 多平台、多店铺资料分散 | `workspace + platform + accountId` 隔离，店铺目录、别名、同步和任务均带作用域 | 降低串店、错店和重复搬运风险 |
| AI 容易编造商品事实 | 商品/SKU/价格/库存先确认，内容模块保留事实来源 | 减少虚假卖点、客诉和返工 |
| 活动价、SKU、素材容易错配 | 活动有效期、SKU 绑定、素材权益/扫描/AI 修改许可门禁 | 减少低级运营事故 |
| 品牌调性和禁用项难复用 | 品牌档案、视觉规则、知识规则、历史偏好和版本冻结 | 多人、多店内容一致 |
| 生文、生图与发布脱节 | 方向、方案、候选、审核、批准、导出、发布组成同一任务状态机 | 从“生成结果”升级为“交付结果” |
| 平台发布失败后不可追踪 | 幂等键、写后查询、unknown 对账、回执和审计 | 降低重复发布和误报成功 |
| 代运营团队难排查 | 运营队列、角色、账务、告警、规则和版本审计 | 支撑多人协作和服务化交付 |
| 用户不愿管理模型 Key | 平台中转站、钱包、成本门禁；用户侧不暴露 Key | 降低安装和安全门槛 |

## P0 商业与工程缺口

1. **订阅订单信任客户端商业参数。** 已修复：`subscription.order.create` 和 `subscription.change` 现在只接受套餐代码与周期，由服务端当前有效的套餐目录冻结价格和权益快照；旧的价格、套餐名、店铺数、任务数字段会被契约层拒绝。加购数量已进入独立 entitlement ledger。
2. **双重付费逻辑难解释。** 主任务生成已改为优先消耗 `includedTasks`，额度耗尽后才从钱包购买超额；失败按实际结算来源退款。SEO、发布、Brief 等钱包动作也已进入统一 `action_ledger`，按动作类型、结算来源和退款状态对账。
3. **扣费单位与真实成本脱节。** 已新增 `model_usage_ledger`，保存 relay request ID、输入/输出 token、总 token 和 provider 成本；图片张数/尺寸、视频秒数等非 token 计量仍需接入 provider 计费字段。
4. **优惠券核销不是订单原子事务。** 已补订单创建失败时的优惠券补偿回滚；支付退款后的券是否恢复仍需产品明确规则。
5. **加购权益只计价未完整发放。** 已补 `subscription_entitlements`，支付回调按订单幂等发放 `platform/image_generation/bulk_sync` 单位，并已接入图片生成、平台连接、即时/异步商品同步的消费与失败返还。
6. **部分非模型动作被描述为模型扣费。** 已扩展 `action_ledger` 动作类型，将同步、平台连接、图片编辑、创意预览与模型动作分开；权益消费以 `entitlement` 结算来源记录，钱包超额仍单独记录。
7. **真实外部闭环缺证据。** 支付、至少一个平台、模型、对象存储和 Worker 必须在同一 staging release 完成一次 canary。

## 模型中转站审计

### 已落实

- 文案、图片、OCR、图片编辑和视频 provider 工厂只接受 HTTPS `MODEL_RELAY_BASE_URL` + `MODEL_RELAY_API_KEY`。
- 生产环境没有中转、固定模型、RPM/TPM/每日成本上限时 fail-closed。
- `content.codex.prepare/commit` 在生产被应用服务拒绝，正式内容只能调用 `content.generate`。
- Key 不进入 MCP 参数或商家响应；失败路径有幂等退款。

### 尚未落实

- 当前机器的 Codex App 仍使用默认 provider；没有配置用户级自定义 `model_provider`。
- 中转站兼容性和真实调用证据未提供。Codex 需要 Responses API；业务服务还需要 Chat Completions、Images 和 Video 路径。
- 已新增 `model_usage_ledger` 保存 provider usage/cost/request id，并在 `workspace.metrics`、`billing.reconciliation` 暴露观测结果；仍需真实中转响应验证成本字段覆盖率。
- 缺中转站断路、超额、重试、缓存命中、部分响应和异步视频的对账测试。

完整配置见 [`codex-app-relay-setup.md`](./codex-app-relay-setup.md)。

## 商业模式建议

### 价值指标

主价值指标应是“活跃店铺 + 可交付任务/成功发布包”，不是 token。Token 是平台成本单位，商家购买的是减少返工、降低错误和更快上新。

### 推荐包装

| 套餐 | 建议月价（验证起点） | 店铺 | 包含行动额度 | 目标用户 |
|---|---:|---:|---:|---|
| 体验 | ¥0 | 1 | 3 个文案交付任务，不开放真实发布 | 验证首次价值 |
| 单店 | ¥99 | 1 | 30 个标准交付任务 | 个体卖家 |
| 多店 | ¥299 | 3 | 150 个标准任务，批量与版本协作 | 成长商家 |
| 代运营 | ¥899 | 10 | 500 个任务、成员角色、运营队列 | 团队/服务商 |
| 企业 | 定制 | 定制 | SSO、审计、专属 SLA/模型策略 | 品牌与大型服务商 |

这是一组实验起点，不是最终定价。当前默认 ¥199/月、1 店、30 任务缺少转化率、续费率、单任务成本和愿付价格证据，不宜直接上线。年付建议先保持约 17% 优惠，等留存数据稳定后再调整。

### 用量与钱包

- 套餐费购买工作区、店铺、治理能力和一批行动额度。
- 文案标准任务消耗 1 个行动额度；高成本图片/视频按明确的图片张数、视频秒数或渲染任务使用更多额度。
- 超额从钱包购买行动包；钱包不应成为每次都与套餐额度并列检查的第二个门槛。
- 中转站成本账本按 token/图片/秒记录，商家前台只展示“本次消耗多少行动额度”和失败退款。
- 目标毛利按功能设置成本底线；视频、高清图片等高波动能力单独定价，不能用统一 1 分扣款。

### 市场锚点

- Shopify Magic 把通用 AI 能力包含在 Shopify 订阅中，说明基础生文/生图本身很难单独收费。
- Jasper Pro 当前为 69 美元月付或 59 美元/月年付，并把品牌知识、协作和治理作为价值核心。
- Shopify 图片/视频类应用常见“免费试用额度 + 月费信用包”，说明高成本视觉能力适合混合订阅和用量包。

大麦不应与免费通用 AI 比“每次生成多少钱”，而应以中国电商多平台真实资料、合规门禁和可发布闭环形成差异化。

## 90 天执行顺序

### 0–30 天：证明可卖

- 选择一个主平台和 3–5 家试点商家，完成 OAuth、读取、一次低风险写入、写后回读和回执导出。
- 接入真实中转站，完成 Codex `/responses` 与业务模型全链路，验收 `model_usage_ledger` 的真实 token/cost 回写。

- 把新会话首页收敛为“店铺、商品、素材、知识库、开始任务”五个入口。

### 31–60 天：验证复购

- 跑 10 个黄金商品任务与模型质量 Eval；记录首次价值时间、人工修改率、P0 漏检和成功发布率。
- 开始 ¥99 / ¥299 两档价格实验和愿付价格访谈。
- 根据真实拒绝、修改和成本数据调整行动额度，不先扩大功能清单。

### 61–90 天：复制能力

- 只有主平台指标达标后，再复制到第二个平台。
- 上线代运营档、成员角色、运营队列与批量交付。
- 完成 50 工作区真实云容量、告警和值班演练。
